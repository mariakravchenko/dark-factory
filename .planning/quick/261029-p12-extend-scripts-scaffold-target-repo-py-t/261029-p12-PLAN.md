<design_decisions>

Settled during planning by reading the real script and the real CLI. Do not re-litigate them; implement them.

**DD-1 — `run.yml` is `resume.yml` with four differences, and nothing else.**
The prior quick task's `RESUME_WORKFLOW_TEMPLATE` is the shape. The new template is a copy of it with exactly four changes: the top-level `name:`, the input block (`run_id` becomes `source`, with its own description), the job key (`resume:` becomes `run:`), and the final step's `name:` and `run:` line. Everything else is byte-identical in structure: the quoted `"on":` key, `permissions: contents: write`, `runs-on: ubuntu-latest`, `timeout-minutes: 30`, `actions/checkout@v4` with `fetch-depth: 0`, the `{{INSTALL_SOURCE}}` pip-install step, the fully-commented "Install the worker runtime" step, and the three fixed `env:` entries followed by the `{{WORKER_CREDENTIAL_ENV}}` token. Indentation nesting must match exactly (`jobs:` 0, job key 2, `steps:` 4, `- name:` 6, `env:` 8, env entries 10) because `render_worker_credential_env_block()` emits its lines at a hardcoded 10 spaces and is shared by both templates.

**DD-2 — `permissions: contents: write` is correct for `run.yml`, reasoned, not copied.**
The question in the task brief is answered by first principles, and the answer is the identical block. A fresh run does *strictly more* writing to the repository than a resume does: it creates the run branch, and after every role it commits that role's artifacts and pushes them (`commit_run_artifacts` + push), then may open a PR. `actions/checkout`'s default credential setup (`persist-credentials: true`) is scoped by exactly this `permissions` block, and it is the only credential channel git has in the job. Scope it to `read` and the first role's push fails with a 403. `fetch-depth: 0` is equally load-bearing for the same reason README already documents: the quality gate's `collect_pr_diff` after-hook runs a merge-base triple-dot diff, which needs full history. Note what is deliberately *not* added: no `pull-requests: write`, because PR creation goes through Dark Factory's own `GITHUB_TOKEN` secret (a PAT supplied by the deployer), never the Actions-granted token — exactly as in `resume.yml`.

**DD-3 — One input, named `source`, required, type string. No second input, no matrix, no second job, no `if:`.**
The value is passed to `dark-factory run` verbatim and must be one of the three literal prefixes the real resolver accepts (`src/dark_factory/input/resolver.py` `_PREFIXES`): `text:`, `spec:`, `github:`. The `github:` remainder is a bare positive integer (the issue number) — owner and repo come from the run's own `.dark-factory.yaml`, never from the locator. The input `description:` must say this accurately. This minimalism is the README's own stated rule for `resume.yml` ("a trigger that grows a branch on run state has started deciding what happens next"), and it applies identically here.

**DD-4 — Reuse every existing mechanism; add no parallel one.**
`render_worker_credential_env_block()` and the module-level `WORKER_CREDENTIAL_ENV_VAR` dict are called, not duplicated — that is what keeps `.env.example`, `resume.yml` and now `run.yml` from drifting (the prior task's DD-5). Registering the new path in the `build_contents()` dict inherits `main()`'s `write_output_file()` loop, its per-file status line and the skip-unless-`--force` guard (DD-7) for free. Adding the path to `_YAML_CHECK_RELATIVE_PATHS` inherits `parse_check()` for free. No new CLI flag is introduced — `--install-source` already parameterizes the pip-install step and now feeds both workflows.

**Scope note — two things deliberately left alone.**
(a) README's "The reference workflow" section and its `resume-workflow-reference` sentinel block are NOT touched and get no `run.yml` sibling block. A test extracts that exact block by those sentinels; its content must stay byte-identical (SHA-1 `d2a767165eb7ef03cdd8248bfa40b754e6a4caf3`).
(b) README line ~347 writes the start command as `dark-factory run github:<owner>/<repo>#<n>`, which does not match the real resolver (`github:` takes a bare issue number). That is a pre-existing inaccuracy in a different subsection and is explicitly out of scope — do not fix it here, and do not propagate that spelling into the new `run.yml` description or the new README prose.

</design_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deployer CLI args -> generated file content | `--install-source`, `--github-*` and `--worker-*` values are substituted into emitted files |
| generated workflow -> GitHub Actions runtime | the emitted `run.yml` declares the permission scope and secret set a CI job will execute under |
| `workflow_dispatch` input -> `dark-factory run` argv | a human-supplied `source` string crosses into a subprocess command line |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-P12-01 | Elevation of privilege | generated `run.yml` `permissions:` block | medium | accept | `contents: write` is the narrowest scope that works, established by DD-2 from first principles and already proven empirically for the resume workflow (narrower scopes produced a 403 on push and a silent empty-worktree fetch). No `pull-requests: write` is granted — PR creation uses the deployer's own `GITHUB_TOKEN` secret, not the Actions-granted token. |
| T-P12-02 | Injection / command execution | `${{ inputs.source }}` interpolation in the generated `run:` line | medium | mitigate | The interpolation is quoted exactly as the already-shipped resume workflow quotes its own input, so the whole value reaches `dark-factory run` as one argv element rather than being word-split or shell-expanded. The verify command asserts the emitted `run:` line is character-exact including both quotes. Triggering the workflow at all requires Actions write access on the target repository. |
| T-P12-03 | Information disclosure | generated `run.yml` `env:` block | high | mitigate | The block names secret *references* only (`${{ secrets.NAME }}`), never values; the names come from the existing static `WORKER_CREDENTIAL_ENV_VAR` mapping, and the script never reads `os.environ` for a credential. The verify command asserts the env key *set* only, never a value. |
| T-P12-04 | Tampering / destruction of existing state | writing `run.yml` into a populated target repo | high | mitigate | The new path is registered in `build_contents()` and therefore goes through the existing `write_output_file()` skip-unless-`--force` guard (prior task's DD-7) with no new code path. Task 1's verify proves it: whole-tree checksum equality across a second non-force run, a surviving locally-added marker line, and a `--force` run that overwrites and removes it. |
| T-P12-05 | Tampering | target-path resolution | low | accept | Unchanged from the prior task's T-OD8-02: `--target` is resolved once with `expanduser().resolve()` and the new output path is one more fixed relative-path constant joined onto it, never a caller-supplied sub-path. This plan adds a constant to that closed set; it introduces no new path-construction code. |
| T-P12-06 | Tampering | README reference-workflow block | low | mitigate | The `resume-workflow-reference` sentinel block is guarded by an exact SHA-1 assertion in Task 2's verify plus the existing `tests/unit/test_resume_workflow_reference_doc.py` suite, so an accidental edit to the documented reference workflow cannot land silently. |
| T-P12-SC | Tampering | npm/pip/cargo installs | low | accept | No package-manager install task exists in this plan. No dependency is added; the script continues to use only the standard library plus PyYAML, already a pinned project runtime dependency approved at a Phase 3 legitimacy checkpoint. No `## Package Legitimacy Audit` is required because nothing is installed. |
