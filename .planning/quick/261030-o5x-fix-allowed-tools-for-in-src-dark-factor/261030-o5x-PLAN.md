<objective>
`allowed_tools_for()` in `src/dark_factory/workers/claude_code.py` translates a role's
`artifacts.write` capability into a single path-scoped `Edit(<artifacts_glob>/**)`
specifier and nothing else. The real `claude` CLI permission-gates its new-file tool and
its existing-file tool as two separate tools, so an Edit-only grant permits only edits to
files that already exist. Every role's first write to any declared output creates a new
file. The result: under `--permission-mode dontAsk` the CLI silently denies that first
write for every role, and the run fails.

This is not theoretical. It was confirmed live against a real target repository's CI run:
the BA role's `requirements.md` and `acceptance_criteria.json` writes were denied and the
run reached FAILED. Dark Factory's own suite never caught it because every test spawns a
fake `claude` script that simulates no permission gating whatsoever -- it writes declared
outputs unconditionally, so the Write/Edit split the real CLI enforces is invisible to the
whole test tree.

Fix: grant both specifiers over the same glob, correct the two pieces of prose that
currently describe a lone Edit specifier, update the two tests that pin the old shape, and
add a regression test that names Write specifically so this exact gap cannot reopen.

Purpose: `artifacts.write` is the one capability every role in the shipped pipeline holds.
With the Write specifier missing, no role can produce its first artifact against the real
CLI -- the adapter is functionally unusable outside the fake-CLI test tree.

Output: a two-specifier `artifacts.write` grant with an unchanged glob, honest docstring
and contract prose, and an assertion that would have failed before this change.
</objective>
