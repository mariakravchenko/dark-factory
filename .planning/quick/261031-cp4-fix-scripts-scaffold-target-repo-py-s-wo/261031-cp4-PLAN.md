<objective>
`scripts/scaffold_target_repo.py` generates two GitHub Actions workflows for a target
repository (`.github/workflows/run.yml` and `.github/workflows/resume.yml`). Both install
dark-factory with `pip`, both carry a commented-out hint for installing the worker runtime
with `npm`-or-whatever that runtime documents -- and neither installs **uv**.

The same script's `DEFAULT_QUALITY_GATE_COMMANDS` is `("uv run pytest -q", "uv run ruff
check .")`, and that pair is written verbatim into the generated `.dark-factory.yaml`'s
`quality_gate.commands`. So the scaffold asks, by default, for a binary its own generated
workflow never installs.

Confirmed live, not inferred: an `app-int` CI run progressed all the way through
BA -> ARCHITECTURE -> DEVELOPMENT -> QA (the `261031-c01` JSON-schema prompt fix held), then
failed at the Quality Gate step with:

    FileNotFoundError: No such file or directory: 'uv'

A GitHub-hosted runner image has no uv on PATH. Four roles' worth of real agent work is
thrown away by a missing two-second install step.

**The fix:** add an `Install uv` step -- the official `astral-sh/setup-uv` Action, pinned to
a major-version tag -- to both templates, positioned before the `Install dark-factory` step.
Then give the script its first regression test asserting that ordering holds in both
generated files.

Three decisions this plan locks:

**1. The step is unconditional.** It is template text, not something rendered only when a
resolved `--quality-gate-command` happens to mention uv. A deployer who overrides the gate
to `make test` pays ~2 seconds and is told by the step's own comment that they may delete
it. Conditional rendering would add a branch, a second code path to test, and a failure mode
where a deployer edits `.dark-factory.yaml` after scaffolding and silently loses the install
step's justification. Unconditional is also what the task description asks for.

**2. The pin is `astral-sh/setup-uv@v6`, read from this repository's own `ci.yml`.** The
task description named `@v3` illustratively; this repository's own `.github/workflows/ci.yml`
already uses `astral-sh/setup-uv@v6` at two call sites, and `v6` is the current major.
Generating a scaffold that trusts an older major than the project's own CI would be a new,
unexplained inconsistency. Task 1's second test asserts the generated ref equals the ci.yml
ref, so the two cannot drift.

**3. No `enable-cache: true`.** This repository's own ci.yml enables it because this
repository has a `uv.lock`. A freshly scaffolded target repository may not, and setup-uv's
cache key globs for exactly such a lockfile. Omitting the option keeps the generated step a
plain two-liner that works in every target repo shape.

**Deliberately out of scope**, and recorded as such in Task 3 rather than silently dropped:
README's hand-copyable `<!-- resume-workflow-reference -->` block carries the identical gap.
It is a separate artifact with its own doc-drift guard
(`tests/unit/test_resume_workflow_reference_doc.py`), and the precedent for splitting it is
this repository's own `261030-mcz` -> `261030-mng` pair, which closed the matching
`permissions:` gap in exactly that order. Also out of scope per the task description: every
file touched by the JSON-schema prompt work (`cli_runtime.py`, `domain/artifacts.py`,
`artifacts/validation.py`).

Purpose: a run that passes four roles must not die on scaffolding that never installed the
tool its own default config calls.
Output: two template edits, one new unit test module, one STATE.md record.
</objective>
