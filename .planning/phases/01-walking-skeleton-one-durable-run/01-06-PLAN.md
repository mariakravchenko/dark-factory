<objective>
The tracer slice. One plain-text task becomes a durable run in Neon, is driven through a real role by `FakeWorker`, and reaches a terminal state — wired end to end through every layer this phase touches, with a runnable end-to-end proof.

**User story framing (MVP mode).** **As an** operator with a task to hand to the factory, **I want to** type `dark-factory run text:"add a health endpoint"` and watch it move `CREATED → BA → COMPLETED`, **so that** I have a durable, resumable, auditable run before a single AI agent is involved.

This is the first plan after which a real user can *do* something. Everything before it built substrate; this one connects the substrate into a working path: input classification, the pure transition function, the one-role pipeline, the resume-first `advance` entry point, the drive loop, and the Typer CLI. It is production-quality, not a prototype — the only stubs are the `spec:` and `github:` loaders, which raise a clean unsupported-source error and can be filled in Phases 4 and 10 without an architectural change.

Every plan after this one refines this slice rather than adding a new layer: Plan 07 proves it survives a crash and a fresh process, Plan 08 adds the `status` read surface, Plan 09 proves the redaction end to end.

    `orchestrator/lifecycle.py`: define `IllegalTransitionError(RuntimeError)` and `transition(state: RunState, signal: Signal, pipeline: Pipeline) -> tuple[RunStatus, str | None, int | None]` returning the next status, next current role and next current step. It is a **pure function**: no `Session`, no I/O, no `WorkerResult` beyond the already-mapped signal. Encode the small legal graph explicitly — from CREATED on ENTER go to the first role's status with that role as current; from a role status on ROLE_COMPLETED go to the next role in the pipeline, or to COMPLETED when the current node is last; from a role status on ROLE_FAILED go to FAILED. Any pair not in the graph raises `IllegalTransitionError`. Enumerating the graph is the feature — it is tiny, reviewable and unit-testable with no database and no mocks, and it is the only code in the system that computes a status change.

    `orchestrator/runner.py`: define `start_run(source_kind, locator) -> UUID` performing classify-then-load-then-`create_run` and returning the id, and `advance(run_id) -> RunStatus` as the single orchestrator entry point. Every `advance` call, without exception: opens a fresh session; calls `load_run_state`; returns immediately when the status is already terminal, performing zero writes; determines the current node from the pipeline snapshot plus `current_role`; executes exactly **one** step; commits it through `apply_transition`; and returns the new status.

    Split the one-role path into two committed steps, per RESEARCH's one-step-granularity recommendation. When the status is CREATED, the step is entering the first role: compute the transition from the ENTER signal, and in one `apply_transition` insert the `role_executions` row with the role, the worker name, a running status and the attempt computed in SQL, set the run's status and current role, and emit ROLE_STARTED. When the status is a role status, the step is running the role: obtain the worker with `registry.get(node.worker)` — a lookup, never a conditional on the name (WORK-03) — build the role context from `RunState`, call `worker.execute(context)` **outside any open transaction**, map the result through `signal_from_result`, compute the next status through the pure `transition`, and in one `apply_transition` update the role-execution row with its status, worker session id and redacted result or error, set the run's status and current role, and emit ROLE_COMPLETED plus RUN_COMPLETED (or, on the failure signal, ROLE_FAILED plus RUN_FAILED). Two `advance` calls therefore carry the one-role happy path, and there is a real committed intermediate state at BA for Plan 07 to kill at.

    Nothing may be carried between `advance` calls. If a step needs a value, it is a column on the run or the role execution, read fresh by `load_run_state` — the workflow snapshot, the normalized task, the status, the current role, the current step, the attempt and both iteration counters. A `NormalizedTask` held across iterations, or an attempt number kept in a Python variable, is the exact signature of a resume path that will diverge from the happy path and then rot unnoticed.

    Bind structlog context at the top of `advance` with the run id, role and attempt, so every log line the step emits is attributable.

    Define `drive(run_id, on_transition) -> RunStatus`: loop calling `advance`, invoke the callback with the previous and new status on each change, and stop when the status is in `STOP_STATUSES`. Use that named constant rather than an inline set — Phase 2 adds WAITING_HUMAN to the stop set and to nothing else (D-06). Bound the loop with a generous maximum iteration count that raises on exhaustion, so a transition-graph bug becomes a loud error rather than a spinning process.

    `cli.py`: build the Typer app with `no_args_is_help=True` and `add_completion=False`. The `run` command takes the source string; it classifies and loads inside a try block, and on `UnresolvableSourceError` or `SourceNotSupportedError` writes the message to stderr and exits 2 — that code is reserved for failures *before* anything is persisted. It then calls `start_run`, echoes the run id on its own line as the first thing on stdout, and only then enters `drive`, printing one line per transition in the `PREVIOUS → NEXT` form (D-04) and finishing with a short summary block naming run id, terminal state, last role and attempt. Printing the id before the loop is load-bearing: a process killed mid-run must still leave the operator something to pass to `resume` (D-01, RESEARCH Pitfall 7).
