<objective>
Build the single place in Dark Factory where lifecycle state changes, and the single place that reconstructs a run from Neon.

**User story framing (MVP mode).** **As** an operator whose laptop lost power mid-run, **I want** the database to hold either the whole step or none of it, **so that** when I run the orchestrator again it finds a consistent run and continues rather than a half-written one it cannot interpret.

Two functions carry the phase's central invariants. `apply_transition()` writes the role-execution row, the `runs` state columns and the `run_events` audit row inside one transaction and commits once — which is what makes a crash between sub-writes a rollback rather than a corrupted run (ORCH-06, SC4). `load_run_state()` reconstructs everything a step needs from columns into a plain value object with no session and no ORM instance attached — which is what makes the happy path and the resume path literally the same code (STATE-08, SC2).

Redaction is applied *inside* `apply_transition()`, at the single call site immediately before each `session.add`, so there is no route by which a JSONB value reaches Neon unredacted (SEC-02, D-14).

Purpose: satisfy ORCH-06, STATE-03's in-transaction attempt computation, STATE-06's columns-not-events rule, and SEC-02's persistence half.
Output: the one mutation path and the one read path, both proven against a real PostgreSQL 17.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller → `apply_transition` | Raw, unredacted payloads cross into the persistence layer here. This is the last point at which a secret can be removed before it becomes durable. |
| `apply_transition` → Neon | The one write surface for lifecycle state and the audit trail. |
| Concurrent processes → the same `runs` row | Phase 1 has no lease, so the `expected_status` guard plus a row lock is the whole concurrency story. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
