<objective>
Build the secret-redaction layer **before** the first line of persistence code exists, and wire it into the two places it will ever be called from: the structlog processor chain and — in Plan 04 — the single lifecycle mutation path.

**User story framing (MVP mode).** **As an** operator who pasted a connection string into a task by mistake, **I want** every persisted event payload and every log line to show `[redacted:database_url]` instead of my password, **so that** a slip while typing a task never becomes an unrecoverable credential leak in the audit trail.

This plan sits deliberately ahead of the schema. SEC-02's whole content is "from the first persistence code, not retrofitted": the moment a `runs` row can be written, `redact()` must already exist and already be the only path. Retrofitting after a leak is not a code change, it is a data-scrubbing incident.

Purpose: satisfy SEC-02 and success criterion SC5 (a task whose text contains a `DATABASE_URL`-shaped value shows redacted values in every persisted event payload and every log line).
Output: `redact()`, the `Settings` object that feeds it live secret values, configured structlog, and a real-sink test helper the SC5 end-to-end proof in Plan 08 reuses.
</objective>

  <context>
    D-14 rates the redaction design **one-way**: a value that reaches Neon or a log file unredacted cannot be recalled, and a value that was over-redacted on the way in cannot be recovered either.     D-15 through D-18 settle most of it: pattern-based redaction covers every `run_events.payload`, every `role_executions.result` / `error`, and every log line. The genuinely open sub-decision is narrower and is the part that touches the operator's own words — what happens to `runs.normalized_task` and `runs.source_ref`, the persisted copy of the task the operator typed.

    D-18 as recorded chooses option A below. Confirm it or change it now; this is the last cheap moment.

    Not in scope for this checkpoint: whether redaction happens at all, the pattern set itself, the `[redacted:<label>]` token format, or the two wiring points. Those are settled.
  </context>
  <options>
    <option id="known-values-only">
      <name>A — Known-value scrub only on persisted task text (D-18 as recorded)</name>
      <pros>A task that legitimately discusses connection-string syntax, quotes a `postgres://user:pass@host/db` example from documentation, or references a commit SHA persists exactly as the operator wrote it, so the BA role in Phase 4 reads the real request. A genuinely leaked live credential — anything matching a `SecretStr` value on the `Settings` object — is still removed everywhere, which is precisely what the Phase 6 and Phase 12 "grep the known secret values across artifacts, events, logs and reports → zero occurrences" checks assert. Event payloads, role results and logs still get the full pattern treatment.</pros>
      <cons>A credential that is real but is not one of Dark Factory's own configured secrets — a third-party API key the operator pasted into the task body — survives in `runs.normalized_task`. It is still scrubbed from every event payload and log line, but the task row itself retains it.</cons>
    </option>
    <option id="full-pattern">
      <name>B — Full pattern redaction on persisted task text too</name>
      <pros>Any credential-shaped string anywhere, including one Dark Factory has never seen, is removed from the task row. Strictly the most conservative posture on data at rest.</pros>
      <cons>Irreversibly mangles legitimate task text. "Add a health check that tolerates a `postgres://user:pass@host/db` URL" becomes "Add a health check that tolerates a `[redacted:database_url]`", and the BA role in Phase 4 is then briefed from a corrupted request with no way to recover the original. The 40-hex classic-PAT heuristic in particular is flagged `[ASSUMED]` in RESEARCH and would clobber git SHAs in prose.</cons>
    </option>
    <option id="dual-column">
      <name>C — Persist both a raw and a redacted copy of the task</name>
      <pros>Nothing is lost and nothing leaks downstream; the redacted copy feeds roles and the raw copy stays for audit.</pros>
      <cons>Puts the unredacted secret in Neon by design, which is the exact outcome SEC-02 exists to prevent, and doubles the column surface every later phase must remember to read from the right one. Rejected on the phase invariant, listed for completeness.</cons>
    </option>
  </options>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Task text and worker output → log sink | The egress boundary this plan exists to hold. Anything reaching a log file has left the process. |
| Environment / `.env` → `Settings` | Where infrastructure credentials enter the process. Everything downstream reads them only through `SecretStr`. |
| `Settings` object → traceback / `repr` | An unhandled exception rendering a settings object would otherwise print a live connection string. |
