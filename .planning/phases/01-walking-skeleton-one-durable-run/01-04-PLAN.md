<objective>
Create the durable substrate: three tables in Neon, one Alembic revision, and a connection layer tuned for a short-lived CLI talking to a PgBouncer-pooled PostgreSQL.

**User story framing (MVP mode).** **As** the Dark Factory orchestrator, **I want** every fact I need to resume a run to live in a typed column in Neon, **so that** a brand-new process on a different machine can reconstruct the run without inheriting a single byte of the original process's memory.

This is the schema that every later phase inherits. Three decisions here are one-way doors — the identifier type, the status-column representation, and the placement of the retry counters — so Task 1 puts them in front of a human before the migration is authored. `01-RESEARCH.md` records them as assumptions A3, A5 and A6 and as Open Question 2, which is exactly the state a one-way decision should not be executed in.

Purpose: satisfy STATE-01 (SQLAlchemy + Alembic + PostgreSQL, `DATABASE_URL` only, no provider-specific logic), STATE-02 (`runs` column set), STATE-03 (`role_executions` one row per attempt) and STATE-06 (`run_events` append-only audit trail).
Output: `runs`, `role_executions` and `run_events` applied and round-tripped against a real PostgreSQL 17, with the ORM and the migration proven not to have drifted.
</objective>

  <decision>Settle the three one-way schema choices before migration 0001 is authored: identifier type, status-column representation, and event-ordering column.</decision>
  <context>
    D-19 is rated **one-way**: once runs exist in Neon, moving or retyping a column is an Alembic migration against persisted rows, not a refactor. Right now the table is empty and every one of these is free to change; after the tracer in Plan 06 runs once against a real Neon project, none of them are.

    Three specifics are genuinely unsettled. `01-RESEARCH.md` flags the identifier type as assumption A3, the status representation as assumption A6, and the `seq` idiom as Open Question 2 — none is a recorded user decision, and all three propagate into every foreign key, every CLI argument, and every later migration.

    Already decided and **not** in scope for this checkpoint: retry counters live as explicit integer columns rather than being derived (D-19 itself); `base_branch` and `working_branch` exist now and stay unused until Phase 5 (D-20); the `artifacts` table is not created in Phase 1 and will store references only, never content (D-21); `run_events` is append-only with the shape given in D-22.

    The recommended combination is A1 + B1 + C1 — that is what `01-RESEARCH.md` reasons toward, and it is the safe default if you would rather not read three sub-decisions.
  </context>
  <options>
    <option id="recommended">
      <name>A1 + B1 + C1 — UUID keys, VARCHAR+CHECK status, BigInteger identity seq (recommended)</name>
      <pros>**A1 UUID v4 primary keys:** a run id is safe to print on stdout line 1, paste into `resume`, and put in a branch name in Phase 5 without leaking a row count or colliding across machines — which matters directly once Phase 11 has two machines writing. **B1 `sa.Enum(RunStatus, native_enum=False)`, i.e. VARCHAR + CHECK:** carries all ten STATE-07 values from migration 0001 with no native PostgreSQL enum type, so a future value change is an ordinary `ALTER TABLE` constraint edit instead of `ALTER TYPE … ADD VALUE`, which cannot run inside a transaction on older PostgreSQL and is awkward under Alembic. **C1 `sa.BigInteger` autoincrement:** SQLAlchemy emits `GENERATED BY DEFAULT AS IDENTITY` on PostgreSQL 17, the modern SQL-standard form, and gives a monotonic gap-tolerant ordering key that does not skew across machines the way `created_at` does.</pros>
      <cons>UUID keys are 16 bytes rather than 8 and index slightly less densely — irrelevant at this scale. A VARCHAR+CHECK status column is marginally weaker at the database level than a native enum type.</cons>
    </option>
    <option id="native-enum">
      <name>A1 + B2 + C1 — as recommended, but a native PostgreSQL ENUM type for status</name>
      <pros>The strongest database-level guarantee that no unknown status value is ever stored, and the enum type is self-documenting in `psql`.</pros>
      <cons>Every future change to the status set becomes `ALTER TYPE … ADD VALUE`, which historically cannot run inside a transaction and is awkward to express in an Alembic revision. All ten values are defined now, so the risk is bounded — but Phase 2's `WAITING_HUMAN` work and Phase 9's gate states are exactly where a set change would surface.</cons>
    </option>
    <option id="bigint-keys">
      <name>A2 + B1 + C1 — as recommended, but BIGINT autoincrement primary keys</name>
      <pros>Smaller keys, denser indexes, shorter run ids to type at the CLI.</pros>
      <cons>A sequential run id leaks how many runs the installation has processed, collides if two databases are ever merged, and is guessable — all three matter once Phase 10 puts run identifiers into GitHub branch names and PR bodies. Changing the key type after rows exist rewrites every foreign key.</cons>
    </option>
  </options>
  <resume-signal>Select: recommended, native-enum, or bigint-keys</resume-signal>
