<objective>
**As a** Dark Factory operator, **I want to** have every capability a role uses checked against that role's configured `tools:` grants on every single invocation, **so that** a role can never quietly do something its configuration never permitted, and the attempt where it tried is recorded in Neon as a first-class, auditable fact.

This plan is the phase tracer plus its first expansion. Task 1 wires **one** thin path through every layer the phase touches: a role's persisted `tools:` grant list → `ToolRegistry.invoke()`'s deny-by-default check → `CapabilityDeniedError` → `orchestrator/runner.py`'s existing failure branch → a persisted `FAILED` role_execution with `CAPABILITY_DENIED` + `ROLE_FAILED` + `RUN_FAILED` events. No MCP, no `build_worker_env`, no `shell.execute` — those are plans 06-02 and 06-03 expanding out from this proven slice.

Purpose: prove the enforcement spine end-to-end on production-quality code, because every later capability, every transport, and the whole credential boundary hangs off `invoke()` being the single place a grant is checked (D-01).
Output: the `dark_factory.tools` package (error hierarchy, `ToolRegistry`, the registered capability implementations, the D-02 native-tool translation table), the `CAPABILITY_DENIED` event type, the D-03 `artifacts.read` production call site, the D-16 QA grant expansion, and the migrated test-config trees.
</objective>

<assumption_delta_decision>
**Primary noun: the capability grant; decision: `no-change`.**

The deterministic scanner fired on the `optional` family — ROADMAP SC5's "the **optional** MCP transport". Re-read against `06-CONTEXT.md` D-01/D-12/D-13 and `06-RESEARCH.md`'s "Don't Hand-Roll" key insight: what becomes optional is a **transport**, not the identity model. The primary noun — the capability grant, keyed by exact capability name and read from the role's persisted `tools:` list — is unchanged and gains no second representation. `ToolRegistry.invoke()` remains the single source of truth for whether a role may perform a capability; MCP is pure protocol translation over it (plan 06-03), and `granted_tools` at MCP-server-construction time is an advertisement list, never a second grant store.

No promote and no add-alongside is warranted: there is no second grant model to promote and none is being added. The one thing that genuinely *does* become plural is the set of **callers** of `invoke()` (orchestrator-owned code, direct tests, MCP tool closures), which is exactly the shape a single enforcement point is supposed to support.

**Companion invariant test (accepted):** `tests/unit/test_tool_registry.py` carries an explicit test that the deny check runs before dispatch and that no second code path can reach a capability implementation without passing through `invoke()` — the registry exposes no public accessor returning a raw implementation callable. This encodes "one enforcement point, N transports" as a contract rather than a convention.
</assumption_delta_decision>

<planner_override>
**Override of the `06-CONTEXT.md` "Artifacts.write production call site" planning note (which explicitly invites the planner to override with rationale — it is architecturally derived, not user-adjudicated).**

The note proposes migrating `actions/builtins.py::store_role_artifacts` onto `registry.invoke('artifacts.write', ...)` while preserving its no-op behavior. This plan does **not** do that, for a reason the note's own premise supplies: `store_role_artifacts` is a **permanent no-op precisely because an action may never be a real mutation-path call site** (WR-01, enforced by `tests/unit/test_single_mutation_path.py`), and it is opted into per role by a `after:` list. A grant check hosted inside a role-configurable hook is a **conditional** check — a role YAML that drops the hook name drops the check with it. Deny-by-default that a role's own config can switch off is not deny-by-default.

What this plan does instead:

1. **`artifacts.read` is migrated exactly as D-03 locks it** — `collect_role_artifacts` (`artifacts/validation.py`), the real, unconditional, every-role-execution call site `orchestrator/runner.py` already makes after every `ROLE_COMPLETED` signal, reads each declared output through `registry.invoke(role, "artifacts.read", granted, ...)`. Deny-by-default for `artifacts.read` is therefore provable end-to-end through the real pipeline, which is exactly what D-03 asks for.
2. **`artifacts.write` gets a real registered implementation** (`write_artifact_text` — genuine content I/O, not a stub) and a real caller: the MCP transport in plan 06-03, where a worker asking Dark Factory to write an artifact goes through `build_mcp_server` → `registry.invoke` → the deny-by-default check. That is the capability's genuine call path — per D-02 the registry never intercepts a worker's own native writes, so the only legitimate orchestrator-mediated `artifacts.write` caller is a worker that asked for it over a transport.
3. **`store_role_artifacts` stays a permanent no-op**, and its docstring is updated to name `collect_role_artifacts` as the site where artifact-tier grants are now enforced and to state why the check cannot live in an action.

This resolves `06-RESEARCH.md` Open Question 2 explicitly (its own recommendation was "decide this during planning"), and it does **not** thread a `ToolRegistry` into `FakeWorker` — the outcome the CONTEXT note was written to prevent.
</planner_override>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| role config → orchestrator | A role's `tools:` list is repo-controlled YAML; it decides what a role may do, so a malformed or over-broad entry is an authorization input |
| orchestrator → capability implementation | The one place a grant is checked; everything past it runs with the role's authority |
| capability caller → filesystem | `repo.*` / `artifacts.*` arguments are paths that must stay inside the run worktree / run root |
