<objective>
**As a** Dark Factory operator, **I want to** expose a role's granted capabilities to a compatible worker over MCP without the orchestrator depending on MCP at all, **so that** an agent runtime that speaks the protocol can use Dark Factory's tools, and an installation that does not want the dependency can delete it and lose nothing.

This plan expands the proven `ToolRegistry` slice outward along the transport axis. The load-bearing idea is the one `06-RESEARCH.md` states plainly: MCP is not a second place capability grants live. `build_mcp_server` advertises a role's granted names as a convenience, and every tool closure it registers calls the same `registry.invoke()` the orchestrator calls — one enforcement point, two transports. The second half of TOOL-05 is the removability claim, proven structurally by an AST guard rather than asserted.

Purpose: SC5 makes two claims — tools are exposed over MCP, and removing MCP leaves the orchestrator fully functional. Both need proof, and the second is the one that quietly rots, which is why it gets a guard with its own sanity companion.
Output: the `mcp` optional-dependency group, `src/dark_factory/tools/mcp_transport.py`, the in-memory client proof, and the import-graph guard.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → tool closure | A protocol peer names a tool and supplies arguments; both are untrusted input crossing into orchestrator authority |
| PyPI → the build | A new third-party dependency and its transitive tree enter the project's supply chain |
| tool closure → capability implementation | The point past which the role's authority applies; the deny check must already have run |
