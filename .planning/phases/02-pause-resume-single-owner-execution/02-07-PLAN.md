    Extend `.env.example` with the two lease knobs, in the file's existing style: variable name, a placeholder value equal to the production default, and a comment saying what it controls, in what unit, and what changing it costs. For the TTL, say that it is how long a claimed run stays owned without a renewal, that a crashed owner's run is unclaimable until it elapses, and that there is deliberately no way to force an earlier steal in this phase. For the heartbeat interval, say that it is how often the owner pushes its expiry forward while a step is in flight, that it must be strictly less than the TTL or settings loading fails, and that the ratio rather than the absolute value is what matters — one third is the standard choice so that two consecutive missed renewals still land inside the TTL.     Extend `README.md` with a Phase 2 section covering the walkthrough an operator actually needs:

    * How to make a run pause. In the walking-skeleton walkthrough the worker is the fake, so document the scripted-result environment variable as the way to produce a needs-input result, and show the command and the expected output — the run id on line 1, the transition line into the waiting status, the summary block, and exit code 0.
    * How to see the recorded question, using the existing status command.
    * How to resume, from a different shell, with the answer option. Show the command, the transitions printed, and exit code 0.
    * What happens when two processes touch the same run at once: the second prints that the run is owned by another process, changes nothing and exits 0. Say that this is a normal outcome and not an error, because a script that treats it as one will retry pointlessly.
    * What happens when a process is killed while it owns a run: nothing else can claim it until its lock expiry passes, which is the TTL by default, after which any process resumes it from the last committed step.

    Update the exit-codes section to the mapping as implemented: 0 for a run that reaches completion, 0 for a run that stops cleanly waiting for a human, 0 when another process owns the run and this one declined to act, 1 for a persisted failure, and 2 for a bad invocation or an orchestration error where nothing new was persisted. Both new zero cases are the ones a wrapper script is most likely to get wrong, so state them explicitly rather than folding them into the completion case.
