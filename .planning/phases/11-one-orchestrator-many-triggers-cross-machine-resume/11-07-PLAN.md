**Gap G-11-2** (severity: major, UAT test 2)

Failed truth: `dark-factory resume <run_id>` inside the dispatched `resume.yml` job resumes
the run to its next state.

Root cause (already diagnosed): README's reference workflow runs
`pip install "dark-factory @ git+..."` and then `dark-factory resume "${{ inputs.run_id }}"`.
The worker adapter assigned to the role being resumed spawns a CLI binary by name; that
binary is on no GitHub-hosted runner by default, is installed by no step in the reference,
and is named nowhere in README's provisioning guidance. The run ended `FAILED` instead of
advancing past BA. The dispatch mechanism itself (D-01/D-02) is proven; this gap is
specifically the deployer-facing documentation's completeness.

**What README already says, and why it was not enough.** Lines 380-384 already tell the
deployer to supply "whichever worker credential your roles' assigned worker needs (e.g.
`ANTHROPIC_API_KEY`)". The user read that, supplied the credential, and still failed —
because a credential is not a runtime. Strengthening only this prose repeats the bet that
already lost. The fix has to appear at the copy-paste site, in the block itself.

**The scope question G-11-2 leaves open, and how this plan resolves it.** The gap's `missing`
list deliberately does not pre-decide whether the shipped reference should carry an example
install step or only prose plus a pointer. Resolved here as **both**, with the install step
*commented out*:

- Prose-only is the option that already failed, one sentence away from the failure point.
- An *active*, uncommented install step would hardcode one agent runtime into a block whose
  entire purpose is worker-agnostic, against CLAUDE.md's "Role != Worker — any role assignable
  to any worker" constraint, and against D-04's "documentation/reference content ... not
  something Dark Factory's own CI enforces exists".
- A commented step sits exactly where the deployer is pasting, is explicitly labelled as
  applying to whichever worker their roles use, does not make Dark Factory ship or endorse one
  runtime, and leaves the existing structural guards satisfied — a YAML comment is not a step,
  so "exactly one `dark-factory resume` step" and "zero `if:` keys" both still hold.

**What this plan deliberately does not do.** It does not name a third-party install command
or package registry for any runtime. Nothing in this repository documents or verifies any
agent CLI's install procedure, Dark Factory does not own it, and pinning an unverifiable
third-party command into a block it also cannot test would be inventing a fact and creating a
drift liability. The deployer is told precisely which binary name must end up on `PATH` —
grounded in the repository's own registry — and pointed at that runtime's own documentation
for how to put it there.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dark Factory documentation -> a deployer's own repository | README's reference block is copied verbatim into a third party's CI. Anything this block instructs runs on their runner with their secrets. |
| the dispatched job -> a third-party agent CLI | The documented install guidance determines what software a deployer places on a runner that holds `DATABASE_URL` and `GITHUB_TOKEN`. |
| `.dark-factory/roles/*.yaml` `worker:` value -> adapter binary spawn | Pre-existing and untouched; listed because the documentation change describes this boundary and must describe it accurately. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-28 | Tampering | the install guidance inside README's copied-verbatim reference block | high | mitigate | A concrete third-party install command in a block deployers paste into their own CI is a supply-chain recommendation Dark Factory cannot verify, cannot pin and does not own; a renamed, transferred or typo-squatted package would be executed on a runner holding `DATABASE_URL` and `GITHUB_TOKEN`. Task 1 therefore forbids naming any install command, package name or registry, and instead names only the `PATH` binary — derived from this repository's own `LIVE_RUNTIMES` — and points the deployer at that runtime's own documentation. Task 2's guard binds the documented binary names to the registry so they cannot drift into something arbitrary. |
| T-11-29 | Elevation of Privilege | the reference workflow's step surface | medium | mitigate | Adding a step to a workflow that already declares `permissions: contents: read` and runs with the deployer's Actions secrets widens what executes beside the resume. Keeping the new step commented out means the paste-time surface is unchanged: nothing new executes until the deployer deliberately enables it, having read the subsection explaining what it is for. Task 1 also forbids adding an `if:` key or a second resume invocation, and Task 2's two pre-existing structural guards (`...resumes_exactly_once`, `...carries_no_run_state_branch`) are in both tasks' verify sets. |
| T-11-30 | Information Disclosure | README's worker-runtime credential table | medium | mitigate | A credential table is a natural place for a real token to be pasted as an "example" and committed. Task 1 restricts the column to the *variable name* (the upper-cased `Settings` field), never a value, and Task 2's assertions check only for the variable-name spelling, so a guard failure can never be satisfied by supplying a value. `.env.example`'s existing placeholder convention remains the only place example-shaped secrets live. |
| T-11-31 | Repudiation | documentation drift after a fourth worker adapter is added | low | mitigate | Prose-only guidance silently becomes wrong the moment a new adapter lands, which is how this gap existed since the adapters shipped. Task 2 parametrizes over `LIVE_RUNTIMES`, so registering a new runtime fails the unit tier until README documents its binary and credential — the registry, not a human's memory, is the source of truth. |
