<objective>
Expand the tracer slice from plan 11-01 outward to its failure surface: the dispatch call now
degrades safely and visibly in every way it can fail, and each degradation is proved against a
real database.

Purpose: plan 11-01 delivered the success path and one ordering proof. A side-channel GitHub call
that follows an already-committed mutation has exactly three ways to go wrong — the API rejects
it, the run's repository is not configured for it, or the process holds no credential for it — and
all three must end the same way: the human's answer stays recorded, the delivery answers `200`,
and the receiver's own logs say what happened. Getting any of these wrong is worse than not
dispatching at all: a 5xx invites GitHub to redeliver a delivery whose answer already committed,
and a silent skip leaves a human waiting forever on a resume nobody can explain.

This follows the precedent `orchestrator/runner.py` already set for the Phase 10
clarification-comment post — fail soft, never silent — but must be written locally in `app.py`
rather than shared: `orchestrator/runner.py` is not on the webhook package's direct-import
allowlist, so this is a parallel independent implementation of the same shape, not a call into
a shared helper.

Output: `webhook/app.py`'s dispatch block grown from one path to four, and four new db-tier tests
in the module plan 11-01 created.

Deliberately NOT in this plan: the success path and its assertions (plan **11-01**); the
two-subprocess cross-machine proof (plan **11-03**); CI tier enablement (plan **11-04**); the
deployer-facing documentation (plan **11-05**).

**Assumption (this plan's own).** The status code for a failed dispatch is `200`, not `503`.
11-CONTEXT.md leaves the fail-soft-vs-fail-loud call to Claude's Discretion and points at Phase
10's clarification-comment precedent, which is fail-soft. The reasoning recorded here for a later
reader: `_RETRY_LATER` (503) exists so GitHub redelivers when the work has *not* been done, and
by the time the dispatch runs the answer is already committed — a redelivery would re-enter
`submit_answer` and hit the `NoPendingInteraction` / `NotWaitingForHuman` arm, i.e. it would
return `200` and still not dispatch. So a 503 here buys no retry and costs a misleading signal.
If a future phase wants dispatch retries they belong in orchestration with a persisted attempt
count, not in the webhook's HTTP status.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions API -> Dark Factory (error responses) | A failed dispatch returns an error whose body can echo request headers, including the `Authorization` header carrying the dispatch token. |
| Dark Factory -> its own logs | The failure detail written by this plan's `webhook.dispatch.failed` record is a value derived from a GitHub response and lands in the receiver process's persistent log stream. |
| GitHub (inbound webhook) -> Dark Factory | Unchanged from Phase 10 — HMAC verification runs before anything in this plan is reachable, and the ignored-delivery test pins that no dispatch happens for a delivery that fails it. |
