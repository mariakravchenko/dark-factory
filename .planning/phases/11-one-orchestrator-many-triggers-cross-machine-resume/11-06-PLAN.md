<objective>
Close G-11-1: `src/dark_factory/webhook/app.py` builds its ASGI application at module
import time, so importing the module requires a reachable database. CI's
`Unit and contract tiers` step deliberately has no `DATABASE_URL` (only the separate
`Database tier` step provisions one, via testcontainers inside its own pytest run), so
collection of the three test modules that import this module dies with a pydantic
`ValidationError` and the job exits 2 — before the `db`-tier step this phase added
(plan 11-04, D-05) ever runs.

Purpose: QUAL-01's claim is "the `FakeWorker` orchestration suite ... runs green in CI."
Right now CI cannot reach that suite at all. This plan removes the import-time database
requirement and installs a guard so the defect class cannot return silently — the failure
was latent since Phase 10 and only surfaced when this phase finally pushed a commit.

Output: a deferred-construction `webhook/app.py`, both docstrings updated to the factory
invocation, and one new unit-tier module that proves database-free importability for the
whole package in a child process.
</objective>

**Gap G-11-1** (severity: blocker, UAT test 1)

Failed truth: the `Database tier (FakeWorker orchestration suite, QUAL-01)` step's
`pytest_report_header` reports the `testcontainers` rung, the `db` tier passes, and
step/job durations sit inside their `[ASSUMED]` timeouts.

Root cause (already diagnosed, confirmed reproducible): `src/dark_factory/webhook/app.py`
line 416 evaluates `build_app()` as a module-level side effect (introduced Phase 10,
commit `0d9ee71`). `build_app()` reaches `settings_factory()` -> `get_settings()` ->
`Settings()`, whose `database_url` / `database_url_direct` fields are required. Three test
modules import this module, so `pytest -q -m "unit or contract"` fails at *collection*.

Reproduced during planning, with the exact traceback the UAT reports:

- `python -c "import dark_factory.webhook.app"` with an `env -i PATH HOME` environment and
  a working directory containing no `.env` raises
  `pydantic_core.ValidationError: 2 validation errors for Settings` naming
  `database_url` and `database_url_direct`, through `app.py:416 -> app.py:183 ->
  settings.py:206`.
- The same sanitized environment running
  `python -m pytest --collect-only` over the three named modules reports
  `Interrupted: 3 errors during collection`, `no tests collected`.
- A sweep of all 73 walked `dark_factory.*` modules under that same sanitized environment
  reports exactly two failures: `dark_factory.webhook.app` (this gap) and
  `dark_factory.tools.mcp_transport` (`ModuleNotFoundError` — the `mcp` optional extra is
  simply not installed in this venv; a configuration fact about the environment, not an
  import-time I/O defect).

**Why the local test run never caught it:** `Settings.model_config` sets
`env_file=".env"`, resolved relative to the process working directory. This repository has
a git-ignored `.env` holding `DATABASE_URL`, so every local `pytest` invocation from the
repo root constructs `Settings()` successfully and the module imports fine. The gap is only
observable when **both** conditions hold: no `DATABASE_URL` in the environment **and** a
working directory with no readable `.env`. Any regression test that forgets the second
condition passes vacuously on a developer machine and lets the defect back into CI. This is
the single most important implementation constraint in this plan.
