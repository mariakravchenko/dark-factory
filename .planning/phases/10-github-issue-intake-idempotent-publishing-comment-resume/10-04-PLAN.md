<objective>
Close the loop. A human replies on the GitHub issue, and the run that asked the question wakes up
— same run, same `RoleExecution`, same lease discipline the CLI already uses.

A new, separate webhook-receiver process (D-01) verifies the delivery's signature before it parses
or reads anything, turns the `issue_comment` payload into a typed event, decides whether it
resolves to a run's pending interaction, and — when it does — calls the existing
`submit_answer(run_id, answer)` directly, in-process, against the same database (D-02). No new
mutation path, no "mark it claimable and hope something picks it up", no pipeline execution at the
network edge.

Purpose: GIT-06, and the second half of the conversation plan 10-03 started. It is also where two
distinct correctness traps live. The first is the self-comment loop 10-RESEARCH.md Pitfall 2
names: GitHub fires `issue_comment` for *every* comment including the one Dark Factory itself just
posted, so a naive resolver answers its own question with the question's own text the instant it
asks. The second is redelivery: GitHub can redeliver the same logical comment under a new
`X-GitHub-Delivery`, which is why D-05 makes the durable dedup key the business-level GitHub
comment id instead of the transport header.

Output: `src/dark_factory/webhook/` (new package — the first non-CLI deployable in this codebase),
`GitHubClient.authenticated_login`, a narrow `github_pending_interaction` read, a
`github_comment_id` keyword on `submit_answer`, and unit plus db proofs.

Not in this plan: unifying the CLI, CI and webhook entrypoints into one trigger surface is
explicitly Phase 11's job (TRIG-01/TRIG-04) — this plan adds a caller of `submit_answer`, not a
generalisation of how runs are triggered. Cross-machine resume is likewise Phase 11.
</objective>

**`src/dark_factory/webhook/resolve.py`** — the resolution decision, written as a pure function so
every branch is testable without a server, a socket or a signature.

Declare the return types first: `ResolvedAnswer` (frozen, `extra="forbid"`: `run_id: UUID`,
`interaction_id: UUID`, `github_comment_id: int`, `answer: str`) and `UnresolvableComment`
(frozen, `extra="forbid"`: `reason: IgnoreReason`), where `IgnoreReason` is a `StrEnum` with one
member per genuine outcome — an action other than created, a pull-request thread, a self-authored
comment, an empty body, no pending interaction. A named enum rather than free text is what lets a
test assert *why* a delivery was ignored and what lets an operator read the receiver's logs later.

`resolve_issue_comment(event, *, session, authenticated_login)` takes the typed event
`githubkit.webhooks.parse` produced, a database session, and a zero-argument callable returning
Dark Factory's own login (injected, so the unit tier needs no GitHub). It returns exactly one of
the two result types and never raises for an ordinary unresolvable delivery. Order the checks
cheapest-and-most-exclusionary first, so an obviously irrelevant delivery costs no database round
trip:

1. Reject any `action` other than `created`. `edited` and `deleted` cannot un-answer an
   interaction that is already `ANSWERED` — D-05's dedup key is the comment id, so re-processing
   an edit would at best be a no-op and at worst overwrite a recorded answer with later text.
2. Reject a payload whose issue carries a `pull_request` field. Dark Factory only ever asks its
   questions on issues (GIT-05), so a pull-request-thread comment can never be an answer.
3. Reject a comment whose body is empty or whitespace-only after stripping — storing an empty
   answer would move a run out of `WAITING_HUMAN` having learned nothing.
4. Look the run up with `github_pending_interaction`, keyed on the owner, repo and issue number
   read off the typed event. Return the no-pending-interaction reason when it yields `None`. This
   is also the check that makes "never creates a new run" structural: this module has no code path
   that writes a `runs` row, and the lookup either finds an existing waiting run or gives up.
5. Reject a self-authored comment two independent ways, both of them (10-RESEARCH.md Pitfall 2,
   Assumption A4): the comment's id equalling the interaction's `clarification_comment_id`, and
   the commenter's login equalling `authenticated_login()`. Read the login off `githubkit`'s typed
   model rather than dict-poking a guessed path, and record in the module docstring which field
   the installed version actually exposes. Keeping both checks means the filter does not rest on
   the unverified identity-field assumption alone.
6. Otherwise return `ResolvedAnswer` with the comment body verbatim — no normalization, no
   escaping, no truncation. The body is untrusted text; it is stored through the one mutation
   path, which already redacts it before it reaches Neon.

This module performs no write of any kind and constructs no ORM row —
`tests/unit/test_single_mutation_path.py` walks the whole source tree.

**`tests/unit/test_webhook_resolve.py`** (new) — cover every behavior above. Build payloads by

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet -> the webhook receiver | An unauthenticated network edge — the widest attack surface this phase opens, and the first non-CLI entry point in the codebase. |
| GitHub -> Dark Factory | Comment bodies and commenter identities are attacker-influenceable: anyone who can comment on the issue can put text into an answer that a role will read. |
| The receiver -> Neon | The receiver shares the database with the orchestrator and can move a run's lifecycle state. |
| Dark Factory -> Dark Factory | GitHub fires `issue_comment` for Dark Factory's own posted question, so Dark Factory is, uniquely here, its own untrusted input source. |
