<objective>
Close the one window a database flag cannot close. Plan 10-06 made the publish step real; this
plan makes it idempotent. Before acting, `run_publish_step` checks the three persisted
identifiers D-06 names together — the working branch, `runs.published_commit_sha` and
`runs.pr_number` — and when the fast path says "no PR recorded" it asks GitHub itself whether a
pull request already exists for this run's head branch before creating one.

Purpose: this is ROADMAP success criterion 3 — "killing the process after the PR API call but
before its identifier is committed, then resuming, yields one PR, not two". 10-RESEARCH.md
Pitfall 1 is explicit that the DB-flag check alone cannot satisfy it: in that exact window
`runs.pr_number` is still NULL on resume, so a check that only reads Neon opens a second pull
request. The codebase already contains the right pattern for this class of problem — the Phase 5
WIP-recovery commit checks git's own state rather than a DB column — and this plan applies the
same principle to GitHub's own state. The DB check stays first and stays the common-case fast
path; the API read fires only on the narrow "Neon says no PR yet" branch.

Output: the three-way check and the GitHub-side existence net inside
`src/dark_factory/orchestrator/publish.py`, a unit suite covering all three partial-completion
points, and a db-tier proof that the crash window yields exactly one pull request.

Not in this plan: the clarification-comment idempotency half of GIT-04 (`clarification_comment_id`
checked before posting) lands in plan 10-03 with the posting itself, and the answering-comment
dedup (`github_comment_id`) lands in plan 10-04 with the webhook handler. The columns for all
three already exist from plan 10-06.

  <action>
Restructure `run_publish_step`'s body into an explicit three-stage decision, keeping its signature
and `PublishResult`'s existing fields unchanged except for one addition.

Add `adopted_existing_pr: bool = False` to `PublishResult`. It records whether the returned pull
request was created by this attempt or found already existing — the fact the caller's
`PR_CREATED` event payload needs so the audit trail can distinguish "opened now" from "already
open", and the fact a reader of Neon needs to answer "did this run open two PRs?" without
querying GitHub. Keep it a plain declared field, not a derived one: it is an observation about
what happened, not a fold over other fields.

**Stage 1 — the `create_pr` gate (unchanged).** Return an all-`None`, no-error result immediately
when `create_pr` is false, before any check and before any call.

**Stage 2 — the fast path over persisted identifiers (D-06).** Read `state.published_commit_sha`,
`state.pr_number` and `state.pr_url` from the `RunState` plan 10-06 widened. Also confirm the
run's working branch is the one the identifiers belong to by comparing
`state.working_branch` against `working_branch_name(run_id)`; a mismatch is a programming error,
not a recoverable state, so raise rather than silently re-publishing onto a different branch.
When `published_commit_sha` and `pr_number` are both set, return a `PublishResult` carrying all
three persisted values with `adopted_existing_pr=True` and issue **no git command and no GitHub
API call at all**. This is the common case on every retry and it must be free.

**Stage 3 — act, with GitHub's own state as the safety net.** Otherwise:
1. When `published_commit_sha` is NULL, run `commit_run_artifacts` and `push_working_branch`
   exactly as plan 10-06 wrote them and capture the pushed SHA with `head_sha`. When
   `published_commit_sha` is already set, skip both — the commit and push already happened and
   re-running them would be a second side effect for the same logical step.
2. Call `client.find_pull_request_for_branch(owner, repo, head_branch=working_branch_name(run_id))`.
   This is the crash-safety net 10-RESEARCH.md Pitfall 1 names, and it is the only thing that
   distinguishes "never attempted" from "attempted, succeeded on GitHub, crashed before the
   commit". Match on head-branch equality only — never on title, author, base branch or recency,
   because adopting an unrelated pull request would silently tie this run to someone else's work.
3. When it returns a pull request, adopt it: return its number and URL with
   `adopted_existing_pr=True`, and issue no `create_pull_request` call. Do not update, retitle,
   reopen or otherwise mutate it — a human may have edited the title or body since the interrupted
   attempt, and a resumed publish step must not revert that.
4. When it returns `None`, call `create_pull_request` exactly once and return the new pull request
   with `adopted_existing_pr=False`.
5. Let a `GitHubError` from *either* call produce a `PublishResult` whose `error` is the redacted
   message and whose `pr_number` is `None`, and never fall through from a failed existence check
   into a create. An unreadable GitHub state is not evidence that no pull request exists; treating
   it as such is precisely the double-PR bug this stage exists to prevent.

Document the ordering in the module docstring in `orchestrator/quality_gate.py`'s register: state
that the persisted-identifier check is the fast path and the API read is the crash-safety net,
that the two are complementary rather than redundant, and name the three partial-completion points
the boundary criterion above enumerates so a later reader can see which branch handles which.

Update the caller in `orchestrator/runner.py` only if the `PR_CREATED` payload should carry
`adopted_existing_pr` — if it should, that is a one-key payload addition and this plan owns it;
otherwise leave `runner.py` untouched so plan 10-03 (which modifies `runner.py` in the same wave)
has no conflict. **Prefer leaving `runner.py` untouched:** put `adopted_existing_pr` into the
`PublishResult` only and let plan 10-05 or Phase 12 decide whether it belongs in the event
payload. Do not add `src/dark_factory/orchestrator/runner.py` to this plan's `files_modified`.
