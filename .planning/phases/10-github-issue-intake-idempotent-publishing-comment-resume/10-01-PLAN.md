<objective>
Make a GitHub issue drive a run all the way to a pull request. `dark-factory run github:152`
stops raising `SourceNotSupportedError` and instead fetches the real issue (title, body,
comments, labels) through one thin `githubkit` wrapper (D-03), and the terminal role's
PASS verdict plus a PASS quality gate now commits, pushes and opens exactly one pull request
whose number, URL and commit SHA are persisted in the same transaction that completes the run.

Purpose: this is the phase's tracer slice — the thinnest production-quality path through every
layer Phase 10 modifies (dependency, external-system wrapper, intake loader, repo config,
settings, schema, the one mutation path, the event catalog, the orchestrator's terminal-role
block). Proving it end-to-end first means an architectural dead end surfaces after one plan
rather than after five. It also lays every persisted identifier the later plans check before
acting: `runs.published_commit_sha` (D-06) and the two `human_interactions` comment-id columns
(D-05) all land here in one Alembic revision, so no later plan needs a second migration.

Output: `src/dark_factory/github/` (new package, D-03), `src/dark_factory/orchestrator/publish.py`
(new), migration `0006_github_publishing_columns`, three new `EventType` members (D-07), the
`repository.github_owner` / `repository.github_repo` and `Settings.github_webhook_secret` config
fields (D-04), a real `_load_github`, the publish step wired into the existing terminal-role
block, `tests/support/fake_github.py`, and unit plus db proofs.

Deliberately NOT in this plan, and where each lands: the GitHub-side existing-PR check that
closes the crash-between-API-call-and-commit window (plan 10-02, GIT-04); the clarification
comment on `ROLE_NEEDS_INPUT` (plan 10-03, GIT-05, D-08); the webhook receiver (plan 10-04,
GIT-06, D-01/D-02); the package-ownership and process-boundary guards (plan 10-05). The

and contract-tested against the fake, because `github/client.py` is the one wrapper for this
external system and splitting its method surface across four plans would serialise every later

<task type="checkpoint:decision" gate="blocking">
  <decision>Fix how a GitHub-sourced run records *which issue it came from*, before any run row exists.</decision>
  <context>
This is a one-way door and 10-CONTEXT.md does not lock it. 10-RESEARCH.md Open Question 2 names
it: `Run.source_ref` and `runs.normalized_task` are written once by `create_run` and are
append-only in practice, and plan 10-04's webhook resolver has to find "the run waiting on issue
N of repo owner/repo" by querying exactly these persisted values. Changing the shape after runs
exist is a JSONB data migration plus a rewrite of the resolver's query, not a refactor.

`NormalizedTask.metadata` is already a free-form `dict[str, Any]` (`domain/task.py:25`) and
`source_ref` is already `str | None` — no schema change is needed for any option. `_load_text`
writes `source_ref=None`; `_load_spec` writes the resolved absolute path. There is no precedent
for a structured `source_ref`, which is why this needs a decision rather than a default.

Option A1 is the researched recommendation and is listed first.
  </context>
  <options>
    <option id="A1">
      <name>Recommended: `source_ref = "{owner}/{repo}#{issue_number}"` and `metadata = {"owner", "repo", "issue_number", "labels", "comment_count"}`</name>
      <pros>Human-legible in `dark-factory runs` / `status` output and in the `RUN_CREATED` event payload, exactly as `_load_spec`'s path is. The webhook resolver queries the three typed `metadata` fields rather than parsing the display string, so the resolution query has no string parsing and no format coupling. `metadata` is already JSONB, already indexable with a later expression index if Phase 11 needs one, and already redacted at the single `create_run` call site. Labels ride in `metadata` where INTAKE-03 wants them without inventing a column.</pros>
      <cons>The same facts exist in two places (`source_ref` string and `metadata` fields), so a future writer could let them disagree; the loader must build both from one set of values. One more JSONB read in the resolver query than a dedicated column would need.</cons>
    </option>
    <option id="A2">
      <name>`source_ref` carries the full issue API URL (`https://api.github.com/repos/{owner}/{repo}/issues/{n}`) and is the only resolution key; `metadata` stays `{}`</name>
      <pros>One source of truth, no duplication. The URL is exactly what the webhook payload's `issue.url` field already contains, so the resolver can compare strings with no parsing at all.</pros>
      <cons>Couples the durable resolution key to an API host name — a GitHub Enterprise deployment, or GitHub changing a URL shape, silently stops matching. Leaves INTAKE-03's labels with nowhere to go. Makes `dark-factory runs` output much less readable than `_load_spec`'s precedent.</cons>
    </option>
    <option id="A3">
      <name>Add dedicated `runs.github_owner` / `runs.github_repo` / `runs.github_issue_number` columns to migration 0006</name>
      <pros>A typed, indexable, NOT-NULL-per-source-kind resolution key; the resolver query is three column equalities with no JSONB at all.</pros>
      <cons>Three source-kind-specific columns on `runs` — the table every origin shares — which is exactly the origin-agnosticism INTAKE-05 and `NormalizedTask`'s whole design protect. Every non-GitHub run carries three permanent NULLs, and a fourth source kind in a later phase would want three more columns. Widens the one mutation path's fixed keyword surface for a fact that already has a home.</cons>
    </option>
