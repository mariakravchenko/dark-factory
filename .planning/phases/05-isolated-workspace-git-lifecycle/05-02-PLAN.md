<objective>
**As a** Dark Factory operator, **I want to** know that a role which stops mid-edit never loses its work and that a worktree in a state the platform cannot reason about stops the run instead of corrupting it, **so that** "durable" means the repository work is as recoverable as the database state is.

This plan expands the proven worktree slice from 05-01 with the two behaviours that make the worktree *durable*: on every role entry, uncommitted work left by the previous role is WIP-committed onto the run's working branch and tied to the recovering attempt, and a worktree found on a detached HEAD fails the role loudly instead of proceeding. It is ROADMAP Phase 5 SC3 end to end.

Purpose: make the run's repository state as recoverable as its database state, using the failure and audit machinery Phases 1-4 already established rather than a new pathway.
Output: the `wip_commit_sha` column and its migration, `dark_factory.git.lifecycle`, a real `ensure_clean_worktree`, a `patch` write mode on the one mutation path, one new audit event type, and the runner's before-hook failure seam.
</objective>

<assumptions>
Flagged, unresolved probe items and adopted research assumptions carried into execution (surfaced, never silently dropped):

- **A-05-05 (RESEARCH assumption A2, adopted with a correction that matters).** RESEARCH proposes making `wip_commit_sha` "sticky" inside `_write_role_execution`'s existing `update` branch (set-never-clear). That fixes half the problem and creates another: the mid-attempt write that persists the SHA would itself be an `update`, and `update` is a **full overwrite** that blind-assigns `status`, `worker_session_id`, `result` and `error` from whatever the caller supplied. A mid-attempt `update` would therefore null the attempt's persisted `result` — which is exactly the column a `RESUMING` attempt reads back to reconstruct its previous `NEEDS_INPUT` `WorkerResult`. A crash after that write would make the run unresumable. This plan therefore adds an explicit third mode, `patch`, which assigns only the non-`None` fields it is given, and leaves the existing `insert` / `update` semantics byte-for-byte unchanged. One mechanism, explicit at the call site, no asymmetric compare-and-set hidden inside a shared branch.
- **A-05-06 (RESEARCH Open Question 2, adopted).** A new `EventType.WIP_COMMIT_CREATED` member is added. `apply_transition` legally accepts `events=()` when the status does not change, so the column could be written silently — but this project's stated core value is that durability and observability are the same requirement, and a real, permanent git commit with no audit row is precisely the gap that claim forbids. The catalog's "declare exactly what you write, nothing more" discipline is honoured because this phase genuinely writes the member.
- **A-05-01 (carried from 05-01, now acted on).** `ensure_clean_worktree` stays an action dispatched through the registry, per D-06's literal wording, and all four shipped role YAMLs gain `before: [ensure_clean_worktree]` so the check fires on every role entry in the shipped pipeline. A role YAML that omits the name forgoes recovery; the action's own docstring states this.
- **A-05-07 (open, carried).** The WIP-commit-if-dirty pass that RESEARCH Pitfall 5 identifies as missing after the *terminal* role — the last role has no "next entry" to recover it — is deliberately **not** in this plan. It belongs with the `COMPLETED` cleanup step, which is plan 05-03's subject, and is resolved there by the checkpoint in that plan.
</assumptions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worktree filesystem → orchestrator | The worktree's dirty state and `HEAD` attachment are untrusted facts about a directory a worker subprocess was free to modify; both are read through `git` rather than by inspecting files directly. |
| action → orchestrator | `ensure_clean_worktree` runs arbitrary git writes inside a role's configured hook list. It communicates outcomes only by raising or by leaving a commit; it has no channel into the database. |
| orchestrator → Neon | The `patch` write mode is a new assignment surface on `role_executions`; every text field it can write still passes through the single `redact()` call site. |
| repo config → orchestrator | A role YAML's `before:` list selects which registered actions run. Names are membership-validated against the action registry at config load, never resolved by attribute lookup or import. |
