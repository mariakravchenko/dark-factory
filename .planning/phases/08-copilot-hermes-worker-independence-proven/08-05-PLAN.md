<objective>
Close CR-01 from `08-REVIEW.md` — the BLOCKER finding that `artifacts.write`/`artifacts.read`,
once *granted* to a role running on `CopilotWorker` or `HermesWorker`, carry no scope
enforcement narrower than "everything the CLI's own filesystem access can reach from `cwd`",
while the code's own comments claim `enforce_write_scope` (ROLE-05) compensates — a claim
that provably cannot hold for this path, because the entire per-run `artifacts/` tree sits
under `.dark-factory/runs/` and `attempt_changed_paths` excludes that subtree from its change
set by deliberate prior design (A-05-15).

Purpose: a role must not be able to read or overwrite another role's artifacts undetected.
This is the project's own threat model, not a general-purpose hardening exercise — the
shipped `QA` role now runs on Hermes holding `artifacts.write` + `artifacts.read`, and the
shipped `ARCHITECTURE` role now runs on Copilot holding the same pair with an empty
`write_scope`. Both can today rewrite `BA`'s `acceptance_criteria.json`, `ARCHITECTURE`'s
`design.md` or `DEVELOPMENT`'s `implementation_summary.json` with zero technical restriction
and zero post-hoc detection. `git/scope.py`'s own docstring already states the principle
this plan extends: "`write_scope` is an authorization control, not a formatting nicety."

Output: `enforce_artifact_scope` — a sibling post-hoc control in `git/scope.py`, wired into
`orchestrator/runner.py` ahead of the artifact collect/commit/push sequence; a negative proof
on both new runtimes; and the two documentation-correctness findings (WR-02, WR-03) closed
against the enforcement posture this plan actually produces.

## The judgment call, decided: option (a), not option (b)

`08-REVIEW.md`'s CR-01 offers two directions and asks for one, justified. **This plan takes
option (a): a sibling post-hoc check that diffs and reverts out-of-role-subtree changes under
`.dark-factory/runs/<run_id>/artifacts/`.** Three facts decide it:

1. **Option (b) breaks a locked decision.** Extending `spawn_is_permitted`'s
   "no-compensating-control -> refuse to spawn" rule to the *granted* case of
   `artifacts.write`/`artifacts.read` would refuse to spawn for `QA` on Hermes and
   `ARCHITECTURE` on Copilot — the two assignments locked by D-04 and used verbatim as
   ROADMAP SC2's own example. It would unship this phase's headline proof to close a gap that
   option (a) closes without touching it.
2. **The write half is genuinely compensable, and cheaply.** `commit_run_artifacts`
   force-adds and commits the run tree after each completed role, so a prior role's artifacts
   are *tracked* on the working branch by the time a later role runs. A later role's
   modification or deletion of them is therefore visible to `git diff --name-only HEAD` over
   the artifacts pathspec, and a newly created foreign file is visible to `git ls-files
   --others --ignored --exclude-standard` over the same pathspec. `enforce_write_scope`
   misses it only because it passes `ARTIFACT_EXCLUDE_PATHSPEC` — not because the information
   is unavailable. A sibling check with the opposite pathspec sees all of it, reuses
   `is_out_of_scope` and `revert_paths`, and invents no new mechanism.
3. **Option (b) would not close the read half either.** No spawn rule and no post-hoc check
   can undo a read. What the review reads as a read exposure is, inside the run's artifacts
   tree, the *intended* posture: `ClaudeCodeWorker` deliberately scopes `artifacts.read` to
   `Read(.dark-factory/runs/<run_id>/artifacts/**)` — run-scoped, not role-scoped — because
   "a worker legitimately reads a prior role's artifact output." The real deviation on
   Copilot/Hermes is reach *beyond* the artifacts tree, which is exactly `repo.read`'s
   breadth. That is a documentation-truth problem (WR-02/WR-03), and Task 3 closes it as one:
   stated plainly, pinned by a test, so a future reader granting `artifacts.read` to a role
   on either runtime knows they are granting `repo.read` in practice.

Option (a) also lands the control where the project's own architecture says it belongs:
orchestrator-side and worker-agnostic, so the boundary holds for all four workers at once
rather than being re-derived per adapter — and it gives `spawn_is_permitted`'s granted case a
real, shipped control to name, which is what makes WR-03's fix an honest statement instead of
a disclaimer.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Role A's worker subprocess -> role B's artifact subtree | Both live inside the same run worktree under `.dark-factory/runs/<run_id>/artifacts/`; nothing in the filesystem separates them, and the subprocess `cwd` reaches both. |
| A granted capability -> the reach a runtime can actually restrict | `artifacts.write`/`artifacts.read` name a scope narrower than `repo.*`; two of the three shipped runtimes can express no such narrowing natively. |
| Worker-written artifact content -> `commit_run_artifacts` -> `push_working_branch` | Tampered content that survives the post-worker checks is committed to the working branch and pushed, after which it has left the machine and a later role's verdict is computed from it. |
| Published design contract (`NATIVE_TOOL_CONTRACT`) -> the reader deciding a future role's grants | A contract that overstates confinement causes an over-grant that looks deliberate in review. |
