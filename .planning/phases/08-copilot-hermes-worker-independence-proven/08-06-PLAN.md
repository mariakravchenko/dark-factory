<objective>
Close G-08-2: repair the shared harness in `tests/integration/test_artifact_scope_enforcement.py`
so the two CR-01 negative-path proofs assert the exit code the CLI actually contracts to return
for a run that reaches terminal `FAILED`.

`_drive_shipped_config` (line 128) asserts `proc.returncode == 0` unconditionally on the
`dark-factory run` subprocess. That assertion was lifted verbatim from a positive-path caller
(`tests/integration/test_real_pipeline_zero_config.py:237`, whose run reaches `COMPLETED`) into a
harness that also serves two negative-path tests whose runs are expected — and explicitly asserted
by those same tests, via `result["status"] != "COMPLETED"` and
`result["status_by_role"][...] == "FAILED"` — to reach terminal `FAILED`. The file is therefore
self-contradictory: it demands a failed run and a success exit code from the same drive.

Per phase-01 decision D-05 (`01-RESEARCH.md:18`), `dark-factory run` exits 0 for `COMPLETED`,
1 for a persisted `FAILED`, and 2 for a bad invocation where nothing was persisted. An
artifact-scope violation that fails the role and the run is exactly "a real, persisted terminal
delivery failure", so exit 1 is contract-correct. `tests/integration/test_exit_codes.py` has
asserted that mapping since phase 01, and `git log -L` on `_drive_and_exit` shows the exit line
untouched since phase 02 — the CLI is not a regression and is **not** in scope for this plan.

This is a **test-only** plan. `src/dark_factory/cli.py` must not be modified. Full investigation:
`.planning/debug/cli-exit-code-on-failed-run.md`.

Purpose: make the CR-01 proof executable and honest. The defect shipped because
`08-05-SUMMARY.md` recorded D4/D5/D6 as collection-verified only — no reachable PostgreSQL 17 in
the authoring sandbox — so the three tests were committed having never run. Closing the gap means
both repairing the assertion and actually executing the suite against a real database.

Output: a repaired `_drive_shipped_config` whose exit expectation is per-caller and
self-checking, and a green UAT Test 2 command set run alongside the D-05 contract guard.
</objective>

Change the signature of `_drive_shipped_config` to take an additional keyword-only parameter
`expected_exit: int`, placed alongside the existing `label` keyword. Give it no default value:
the whole defect is a positive-path expectation silently inherited by negative-path callers, so
a future fourth caller must be forced to state its own. Keep every other parameter, the return
type, and the returned dictionary exactly as they are.

Replace the harness's hardcoded success-exit assertion on the `dark-factory run` subprocess with
one that compares `proc.returncode` against `expected_exit`, keeping the existing diagnostic
message shape (the observed code plus captured stdout and stderr) so an unexpected exit is still
debuggable from the failure output alone. Leave the assertion in its current position, before
`run_id` is parsed from stdout line 1, so a bad invocation that persisted nothing still fails
here rather than in a `UUID` parse.

Add a module-level frozen set of the terminal run-status values that the CLI maps to a success
exit — `COMPLETED` and `WAITING_HUMAN` — with a comment naming decision D-05 and pointing at
`src/dark_factory/cli.py`'s own module docstring as the published source. This mirrors the
hardcoded-code idiom `tests/integration/test_exit_codes.py` already uses; do not import the
CLI's private `_CLEAN_FINALS`.

Inside the existing `with Session(engine)` block, after `status_value` is read from `run.status`,
add a cross-check asserting that "the caller expected the success exit code" and "the run's
terminal status is one of the success-mapped statuses" agree as booleans. Its failure message
must name both the expected exit code and the observed terminal status, and say that the two
contradict D-05. This assertion is what makes the harness a second guard on the contract rather
than merely a consumer of it: it is unreachable while the CLI honours D-05, and fires the moment
the mapping drifts (for example if `dark-factory run` were ever changed to exit 0 on a persisted
`FAILED`, which would make the returncode assertion pass while the run had genuinely failed).
That drift is precisely the wrong fix for this gap, so the suite must reject it.

Update the harness docstring to record that the exit expectation is now the caller's to state,
and why: the two tamper callers drive runs to terminal `FAILED`, which D-05 maps to exit 1, while
the untampered control reaches `COMPLETED`, which maps to exit 0.

Update all three call sites to pass their own expectation: the Hermes tamper test
(`label="hermes-tamper"`) and the Copilot tamper test (`label="copilot-tamper"`) each expect the
persisted-failure exit code, and the untampered positive control (`label="no-tamper"`) expects
the success exit code.

Change nothing else. Every existing assertion in the three test functions — run not `COMPLETED`,
