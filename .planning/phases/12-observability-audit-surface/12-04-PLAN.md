<objective>
Complete the event catalog: the acceptance-criteria verdict becomes a first-class,
queryable fact rather than something an operator has to infer from the presence of
a `ROLE_BOUNCED` event or by reading a committed `verdict.json`.

Purpose: `QA_FAILED` / `QA_PASSED` and `QUALITY_GATE_FAILED` / `QUALITY_GATE_PASSED`
answer two genuinely different questions — "did the work meet the stated acceptance
criteria?" and "did the independent command re-run pass?" — and a run can fail the
first while never reaching the second. Collapsing them, or inferring one from the
other, is how a reconstructed run story becomes wrong rather than merely thin.

Output: the final two `EventType` members, their emission alongside (never instead
of) `ROLE_COMPLETED`, and a db-tier cardinality proof across PASS, FAIL-under-cap
and FAIL-at-cap.

## Phase Goal (verbatim from ROADMAP.md — deliberately NOT restated as a user story)

> For any run, Dark Factory can say exactly where it is and retell everything that
> happened to it — the observability half of the durability thesis.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker-authored `verdict.json` content → durable `run_events.payload` | The criterion ids placed in a `QA_FAILED` payload come from a file an external agent runtime wrote. |
| in-memory verdict decision → durable event row | A verdict event that outlives a failed commit is a permanent false claim about what the run did. |
| `EventType` enum surface → every observability consumer | A member nothing writes is indistinguishable, from the outside, from a member whose emission is broken. |
