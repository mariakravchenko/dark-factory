<assumption_delta_decision>
Phase 3 converts three constants into parameters: (a) the hardcoded single-role `DEFAULT_PIPELINE` -> an N-role sequence read from `workflow.roles`; (b) role behaviour hardcoded in `roles/registry.py::ba_role` -> per-role YAML + instruction Markdown; (c) the pipeline resolved implicitly at import -> an effective-config snapshot resolved once at run creation. This is a `chosen` / `derived->chosen` delta (a configuration decision becoming a modeling decision).

- **Noun now primary:** the *effective-config snapshot* persisted on `runs.workflow` at creation. The pipeline is one projection of it (`pipeline_from_snapshot(state.workflow)`); role instructions, tools, permissions, before/after hooks and outputs are other projections.
- **Decision:** `promote` — the snapshot is authoritative on every resume. `DEFAULT_PIPELINE` and `roles/registry.py::ba_role` demote to test fixtures; no production code path defaults to them after this plan.
- **Rationale:** a run's behaviour must be reconstructable from Neon columns alone (invariant "every resume input is a persisted column"); a live module constant cannot be edited per-run and cannot survive a config edit during a pause (SC3).
- **Suggested invariant test (satisfied here):** "every resume executes the snapshot's role order, for any `workflow.roles` the run was created with" — covered by `test_config_drives_pipeline.py` (SC1) and, in 03-04, `test_snapshot_survives_edit.py` (SC3).
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI cwd → config loader | `run()` reads `.dark-factory.yaml` from `Path.cwd()` — an operator-controlled directory. A malformed or hostile file must fail before any run row exists. |
| config loader → run creation | `start_run` turns the resolved snapshot into a persisted `runs.workflow`. A snapshot that reached persistence with a bad role name would fail deep in `transition()` under the lease. |
| persisted snapshot → resume path | `advance` / `drive` rebuild the pipeline from `runs.workflow`. If the resume path could re-read the file, an edit during a pause would change the pipeline (SC3 violation). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-05 | Tampering (of run determinism) | `advance()` / a helper re-reading `.dark-factory.yaml` on resume, yielding a different pipeline than the run started with | high | mitigate | `_advance_once` builds the pipeline from `state.workflow` only; `runner.py` does not import `config.loader` (`cli.py` does); `tests/unit/test_orchestrator_no_live_config_read.py` asserts the four orchestrator/pipeline import closures exclude `dark_factory.config.loader` |
| T-03-09 | Tampering | A `workflow.roles` entry that is not a `RunStatus` value reaching persistence, then a bare `ValueError` deep in `transition()` under the lease after the `runs` row exists | high | mitigate | `WorkflowConfig.field_validator` rejects it at load (03-02); `start_run` raises `ConfigError` before `create_run`; `test_bad_config_no_orphan_run.py` proves the `runs` count is unchanged |
| T-03-10 | Elevation | `pipeline_from_snapshot` or `start_run` silently falling back to a hardcoded `[BA]` pipeline when the snapshot is absent, executing the wrong delivery flow | medium | mitigate | `start_run`'s `snapshot` has no default (a caller error, raised); `DEFAULT_PIPELINE` and `_workflow_snapshot` removed from `runner.py` (grep gate in Task 1) |
