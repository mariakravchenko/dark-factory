## phase4-artifact-commit-bugs — three db/integration tests fail because stale role fixtures declare `write_scope: []` (D-14 zero tolerance) while their own workers write non-artifact files
- **Date:** 2026-09-20
- **Error patterns:** `AssertionError: assert 'source_edit.txt' in []`, `assert <RunStatus.FAILED> is <RunStatus.COMPLETED>`, `assert <RunStatus.FAILED> is <RunStatus.DEVELOPMENT>`, WriteScopeViolation, write_scope, enforce_write_scope, ROLE_COMPLETED becomes ROLE_FAILED, run unexpectedly FAILED, staged file disappears, empty staged list, git rm --cached, git clean, revert_paths, D-14, zero tolerance, artifact commit, worktree
- **Root cause(s):** Stale TEST FIXTURES, not a production defect. Three tests declare a role `permissions: write_scope: []`, which under D-14 means ZERO TOLERANCE (a path matches none of zero patterns, so EVERY changed path is a violation — `scope.py:92` and its docstring explicitly forbid an empty-list early return), while that same test's own worker/fixture plants a non-artifact file in the worktree. At `Signal.ROLE_COMPLETED`, `runner.py:944-958` runs `enforce_write_scope`, which reverts the planted file (`git rm --cached` + `git clean` for a path absent from HEAD) and raises `WriteScopeViolation`, flipping the signal to `ROLE_FAILED` -> `RUN_FAILED`. The fixtures predate phase 5 plan 05-04's D-14 enforcement and were never updated to authorize what their own workers write; their `tools:` lines WERE updated for phase 6, their `write_scope:` lines were missed for phase 5.
- **Fix:** Test-defect fix, ZERO production changes. Each failing test's role `write_scope` widened to name EXACTLY the one non-artifact file that test's own worker writes — never by slackening a shared default. `_write_four_role_tree`: BA stays `[]`, ARCHITECTURE/DEVELOPMENT/QA get `[source_edit.txt]` (all three needed, because the pathspec-limited artifact commit leaves the file staged so every later role's enforcement still sees it). Trailing-edit test: per-test in-place patch of the shared-factory BA YAML to `[trailing_edit.txt]`, with an assertion that fails loudly if the conftest YAML is reformatted. `_write_two_role_tree`: BA gets `[feature.py]`, DEVELOPMENT deliberately kept at `[]`. `tests/conftest.py` deliberately untouched so sibling zero-tolerance tests keep the empty-list default.
- **Files changed:** tests/db/test_artifact_commit_per_role.py, tests/integration/test_pr_diff_excludes_artifacts.py
- **Why not caught:** The detection gate worked; the response gate did not exist. The db/integration tier caught this the moment D-14 enforcement landed and reported it correctly for two phases — but it was triaged as "pre-existing, unrelated to this phase" in 06-01-SUMMARY.md and carried forward as an accepted "662 passed / 3 failed" baseline through 06-04-SUMMARY.md and 06-VERIFICATION.md, so the red count stopped carrying information. Secondary and genuine: **no gate existed for the class** "a config field changes from inert to enforced and existing fixtures declaring the permissive-LOOKING value are not swept" — nothing statically links "this role declares `write_scope: []`" to "this role's worker writes files". Aggravating (not causal): db/integration need a real PostgreSQL 17, so they are absent from the fast inner loop, raising the cost of running them and making a red baseline easy to tolerate.
- **Recurrence guard:** The three tests themselves are now the regression guard — they pass ONLY while each role authorizes exactly the file its own worker writes, so narrowing a `write_scope` back to `[]` re-breaks them immediately: `tests/db/test_artifact_commit_per_role.py::test_one_artifact_commit_per_role_force_added_and_source_edits_survive`, `tests/db/test_artifact_commit_per_role.py::test_completed_run_with_a_trailing_edit_gets_a_recovery_commit_then_loses_its_worktree`, `tests/integration/test_pr_diff_excludes_artifacts.py::test_pr_diff_excludes_dark_factory_and_ignores_the_base_branchs_own_post_cut_commit`. Plus inline D-14 polarity comments at every edited `write_scope` (so `[]` cannot be re-introduced as "unrestricted"), and a loud assertion that fails if the shared `config_root_factory` YAML is reformatted rather than silently no-opping the in-place patch. Recommended but NOT implemented: treat any db/integration failure as a phase-verification blocker rather than a documentable baseline, and require a fixture sweep whenever a config field moves from inert to enforced.
- **Pattern for future sessions:** When a run unexpectedly reaches `FAILED`, or a file you just staged vanishes from `git diff --cached --name-only`, check the role's `write_scope` FIRST — `[]` means deny-all, not allow-all. Confirm with the sibling-control technique: a test using the same empty default that writes nothing and never reaches `ROLE_COMPLETED` will pass, which cleanly splits pass/fail and proves single-cause.

## ci-unit-tier-settings-validation-g-11-3 — 12 unit/contract tests fail only in real CI because production frames call the process-global `get_settings()` on conditionally-taken branches and `Settings` requires `DATABASE_URL`, which a CWD-relative `.env` silently supplies locally
- **Date:** 2026-10-07
- **Error patterns:** `pydantic_core._pydantic_core.ValidationError: 2 validation errors for Settings`, `database_url: Field required [type=missing, input_value={}, input_type=dict]`, `database_url_direct: Field required`, green locally / red in GitHub Actions, green in CI / red locally, `828 passed, 12 failed`, `Interrupted: 2 errors during collection`, get_settings, lru_cache, cache_clear, env_file=".env", SecretStr, pydantic-settings, "No database" docstring, unit test needs no database, settings override, monkeypatch setenv DATABASE_URL, settings_factory, known_secrets, push_token, real_log_sink, configure_logging, credential_missing, skip_reason
- **Root cause(s):** A three-condition AND — no single cause is sufficient, and any single-cause framing produces an under-scoped fix. (1) PRODUCTION: three frames call the process-global `get_settings()` on conditionally-taken branches that unit tests legitimately reach — `logging.py:37`/`:28` via `configure_logging` (which has a `logger_factory` seam but no settings seam), `publish.py:272` (the push-token read inside `run_publish_step`, which ALREADY receives the settings-derived `known_secrets` as a parameter, so the token is the one value violating the function's own contract), and `runner.py:1685` plus un-fired siblings at `:1271`/`:1415` inside `_run_current_role` (which already has four other injection seams). (2) TEST INFRASTRUCTURE: the four Phase-10 files reaching those branches adopted NEITHER of the two settings-override idioms already in use at 14 sites — Idiom A (`setenv DATABASE_URL` + `get_settings.cache_clear()`) or Idiom B (`monkeypatch.setattr(module, "get_settings", ...)`). Three of the four docstrings assert "No database" — correct that they never open a PostgreSQL connection, wrong because `Settings` CONSTRUCTION requires `DATABASE_URL` to be PRESENT. Requiring a URL string is not the same as requiring a reachable server. The same phase's plan 10-01 applied Idiom B correctly; 10-02/03/04/06 did not carry it forward. (3) ENVIRONMENT (the MASKING mechanism): `Settings.model_config` sets `env_file=".env"`, a CWD-relative path, so every local run from the repo root silently satisfies both required fields from the git-ignored `.env`. Remove any one condition and all 12 failures disappear — proven by control runs.
- **Fix:** Applied by gap-closure plan 11-09, verified (not re-applied) by the resumed debug session, which changed no source. SINK B — PRODUCTION, the only change improving production design: `run_publish_step` now takes `push_token: str | None` (`publish.py:127`, consumed at `:275`), threaded from the runner which already held `gate_settings`; removes the hidden global read and fixes 6 tests with zero mocking. SINK C — test-side Idiom B rather than a `settings_factory` seam (`grep settings_factory src/dark_factory/orchestrator/runner.py` returns nothing); covers all three runner sites at the test boundary. SINK A — `tests/support/log_sink.py::real_log_sink` supplies the two fake vars ONLY when absent and clears/restores the lru_cache, fixed once in the shared helper so all 5 call sites and every future caller inherit it. LATENT SIBLING — `tests/support/live_runtime.py:104-105` wraps `get_settings()` in `try/except ValidationError` so an unconstructible `Settings` reads as "credential missing" instead of aborting collection.
- **Files changed:** src/dark_factory/orchestrator/publish.py, tests/support/log_sink.py, tests/support/live_runtime.py, tests/unit/test_unit_tier_needs_no_database.py (plus test-side Idiom B overrides in the four Phase-10 files)
- **Why not caught:** No gate ran the unit tier under a sanitized environment. 11-06's guard proves an IMPORT-TIME property over the `dark_factory` package via a `pkgutil.walk_packages` sweep plus `--collect-only` for three named modules — by construction it cannot observe a `get_settings()` call during test EXECUTION on a conditionally-taken branch, and it never imports anything under `tests/`. 11-06 was correctly scoped to G-11-1 and is not at fault; the runtime analogue of its property simply never existed. Aggravating: the CWD-relative `.env` made every local run green for two phases, so the missing gate cost nothing until this branch's first real CI push, and a LATENT SIBLING (two `tests/integration/*_live.py` modules aborting collection) stayed hidden behind a third condition — the hosted runner has no agent CLIs on PATH.
- **Recurrence guard:** `tests/unit/test_unit_tier_needs_no_database.py` — 3 tests, the runtime analogue of 11-06's import-time guard. Test 1 spawns a child `pytest` over the full `unit or contract` selector READ OUT OF `ci.yml` (not restated, so the guard cannot drift from CI) with `cwd=tmp_path` (no readable `.env`) and an explicit env allowlist omitting `DATABASE_URL`/`DATABASE_URL_DIRECT`, asserting exit 0. Test 2 puts stub agent binaries on PATH to be the collection adversary for the latent sibling, so it cannot hide behind CLI absence. Test 3 is the positive control: a throwaway test calling `get_settings()` unguarded must fail, proving Tests 1-2 are not passing vacuously. Verified load-bearing by mutation: reverting `log_sink.py`'s `supplied` list to `[]` reproduced byte-for-byte the five original `test_webhook_signature.py` node ids.
- **Pattern for future sessions:** When a test suite is green locally and red only in CI (or the reverse), suspect an AMBIENT-ENVIRONMENT dependency before suspecting the code — and check CWD-relative config resolution (`env_file=".env"`) first, because it makes the defect invisible from the repo root. Reproduce by running from a scratch CWD with `env -u VAR` and `-c <repo>/pyproject.toml` so markers/rootdir still resolve — this needs no mutation of the working tree. Three high-value techniques from this session: (a) `--tb=native` frame aggregation (`grep 'File ".../src|tests' | uniq -c`) collapses N failures onto a small set of distinct SINKS, converting a 12-test mystery into 3 targets; (b) the SIBLING-BRANCH control — when only some tests in a file fail, diff the failing and passing tests' fixtures to find which ARM reaches the sink, which proves the distribution is branch-shaped not file-shaped and that test-count is a poor proxy for exposure; (c) always MEASURE a stated constraint rather than trusting it — this file's own "those tests become vacuous" claim was disproved by mutation (the mutant survived, 4 passed, because a pattern rule in `events/redaction.py:120` masked the exact-value path). Also: a docstring claiming "no database" means the author reasoned about CONNECTIONS, not about CONSTRUCTION — treat it as a smell, not evidence.

## cli-exit-code-on-failed-run — two negative-path integration tests fail because a SHARED harness hardcodes `assert proc.returncode == 0`, an assertion copy-pasted from a positive-path caller, on runs the same tests assert must reach terminal FAILED
- **Date:** 2026-10-07
- **Error patterns:** `AssertionError: exit=1 (expected 0)`, `AssertionError: exit=1 expected=0`, `assert proc.returncode == 0`, `4 passed, 2 failed`, returncode 1 instead of 0, CLI exits non-zero, `dark-factory run` exit code, D-05, `_CLEAN_FINALS`, `typer.Exit(code=0 if final in _CLEAN_FINALS else 1)`, QA->FAILED, ARCHITECTURE->FAILED, run reached FAILED correctly, artifact scope violation reverted, enforce_artifact_scope, CR-01, `_drive_shipped_config`, `_run_cli_against_real_repo`, shared harness, negative control, positive control, G-08-2
- **Root cause(s):** Single cause for the FAILURE — a TEST DEFECT with ZERO production defect. `tests/integration/test_artifact_scope_enforcement.py:128` (pre-fix), inside the SHARED harness `_drive_shipped_config`, hardcoded `assert proc.returncode == 0`. That assertion was lifted verbatim from `test_real_pipeline_zero_config.py:237` — a POSITIVE-path test whose run reaches `COMPLETED`, where exit 0 is correct — into a harness that also serves two NEGATIVE-path tests whose runs are expected, and explicitly asserted by those same tests (`result["status"] != "COMPLETED"`, `status_by_role[...] == "FAILED"`), to reach terminal `FAILED`. Per phase-01 decision D-05 (`01-RESEARCH.md:18`, restated in `src/dark_factory/cli.py`'s module docstring), `run` exits 0 for `COMPLETED`/`WAITING_HUMAN`, 1 for a persisted `FAILED`, 2 for a bad invocation that persisted nothing. An artifact-scope violation that fails the role and the run IS "a real, persisted terminal delivery failure", so exit 1 is contract-correct. The tests were therefore self-contradictory: they demanded a FAILED run AND a success exit code. The split is exactly "4 passed, 2 failed" because only the untampered positive control genuinely reaches `COMPLETED`. Separately, the ESCAPE (why it shipped) is a genuine AND of (wrong assertion authored) AND (no reachable PostgreSQL in the authoring sandbox, so `08-05-SUMMARY.md` coverage D4/D5/D6 record all three tests as "collection-verified clean; not execution-verified" — they were committed having never run; the UAT session was their first execution).
- **Fix:** Test-only, ZERO production changes — `src/dark_factory/cli.py` deliberately untouched, since changing the CLI would have broken `tests/integration/test_exit_codes.py::test_exit_1_when_the_worker_script_supplies_a_failed_result` and reversed a decision D-05 itself flags "Reversibility: costly — the Phase 11 CI trigger encodes these three codes." `_drive_shipped_config` gained a keyword-only `expected_exit: int` with NO DEFAULT (`:112`), so a future caller cannot silently inherit another caller's expectation — the exact mechanism that caused the bug. The hardcoded assertion became `assert proc.returncode == expected_exit` (`:145`), and the three call sites now state their own expectation: `expected_exit=1` for hermes-tamper (`:216`) and copilot-tamper (`:281`), `expected_exit=0` for the positive control (`:344`). Added guard at `:176-181`: the harness cross-checks the caller's expectation against the terminal status read back from Postgres — `(status_value in _D05_SUCCESS_STATUSES) == (expected_exit == 0)` — so a stale expectation fails loudly instead of silently re-encoding itself. Note the fix landed in `7b752fe` during phase 08-06; the resumed debug session found it already present and ran the fix-acceptance guardrail rather than writing code.
- **Files changed:** tests/integration/test_artifact_scope_enforcement.py (commit 7b752fe, 1 file, 41 insertions — test-only)
- **Why not caught:** **No gate existed for this class, and still does not.** `.github/workflows/ci.yml` runs `unit or contract` and `db`, but lines 55-59 deliberately EXCLUDE the whole `integration` tier with the documented reason "some of its tests drive real agent CLIs whose credentials (e.g. `ANTHROPIC_API_KEY`) this hosted runner does not have" plus an explicit "Do not 'fix' this omission by adding `integration` to a selector below without first provisioning those credentials." So nothing automated ever executed these tests. The detection gate that DID exist worked correctly as far as it goes: `tests/conftest.py:142` raises `pytest.UsageError` (not skip) when no PostgreSQL 17 is reachable, so an unrun integration test cannot silently pass — but that only fires if someone runs it. Aggravating: the authoring sandbox had no Docker, no local `initdb`, and no `DARK_FACTORY_TEST_DATABASE_URL`, so the author could not run them even in principle; and `08-05-PLAN` said "drive the run in process" while the executor used the CLI-subprocess idiom instead, inheriting the positive-path template's assertion along with it.
- **Recurrence guard:** Two in-code guards from `7b752fe`, both verified load-bearing by revert-check (reverting the hermes-tamper caller to `expected_exit=0` reproduced the original symptom byte-for-byte: `AssertionError: exit=1 expected=0`, 1 failed): (a) `expected_exit` is keyword-only with NO default, so the silent-inheritance path that caused this is now a `TypeError` at call time rather than a wrong assertion at run time; (b) the `_D05_SUCCESS_STATUSES` cross-check at `test_artifact_scope_enforcement.py:176-181` fails loudly whenever a caller's claimed exit code and the persisted terminal status disagree with D-05, so the test cannot drift back out of sync with the contract. Regression tests holding the contract: `tests/integration/test_artifact_scope_enforcement.py` (3 tests: 2 tamper + 1 positive control) and the pre-existing D-05 guard `tests/integration/test_exit_codes.py` (4 tests). NOT implemented, tracked as its own debug session `integration-tier-excluded-from-ci-credential-free-tests-could-run`: these three tests need NO real credentials (they install fake hermes/copilot/claude CLIs via `tests/support/fake_*_cli.py` and monkeypatch fake tokens), so a CI-runnable selector for the credential-free integration subset would close the escape gate that let this ship.
- **Pattern for future sessions:** When some tests in a file fail and others pass, and ALL of them route through ONE shared harness, the defect is almost certainly IN THE HARNESS and the pass/fail split tells you which polarity it was written for — here the single positive control passed and both negative cases failed, which is the copy-paste-from-a-positive-path signature. Three cheap techniques that settled this before any code was changed: (a) read the FAILING test's OWN other assertions for self-contradiction — these tests asserted `status == "FAILED"` and exit 0 simultaneously, which is a defect signature, not a contract claim; (b) DIFFERENTIAL against a correctly-written sibling — `test_role_reassignment_sc2.py:292` is also a negative test and deliberately omits any returncode assertion while its positive sibling at `:158` asserts 0, so the presence of the assertion in a negative path IS the bug; (c) `git log -L <lines>:<file>` on the disputed production function — three commits, all phases 01-02, byte-identical at the failing test's own commit, which REFUTES "regression" in one command. And always check whether a dedicated contract guard already exists (`test_exit_codes.py`): if two tests in the repo cannot both be right, the one encoding a recorded decision wins. Finally — on resume, verify the fix is still absent before writing it: this fix had already landed four phases earlier, so the session's real job was the acceptance guardrail, and the revert-check was what proved the existing fix non-vacuous.
