<objective>
Add the observability half of the durability thesis: a command that says where a run is, sourced from the columns that decide where it is.

**User story framing (MVP mode).** **As an** operator holding a run id and no idea what happened, **I want to** type `dark-factory status <run-id>` and see the run's state, role and attempt, **so that** I can tell whether to resume it, and **I want** `--json` so a CI step can ask the same question.

The requirement here is not "print some fields" — it is *where the fields come from*. STATE-06 and success criterion SC3 both say the current position is read from state columns and never recomputed by folding the event log. That is checkpoint-not-replay, and it is what makes a resume decision trustworthy: if a malformed or missing event could change what `status` reports, then the audit log would silently be the control state, and the whole checkpoint design would be a fiction.

So this plan enforces the boundary structurally as well as behaviourally: `read_status` lives in the observability tier, does not import the events module, and is proven correct with the event log deliberately vandalised.

Purpose: satisfy STATE-06's columns-not-events rule, STATE-02 and STATE-03's field visibility, and success criterion SC3.
Output: `dark-factory status <run-id>` and `--json`, proven invariant under event-log mutation.
</objective>
