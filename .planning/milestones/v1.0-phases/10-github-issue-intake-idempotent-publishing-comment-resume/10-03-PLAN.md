<objective>
Give a GitHub-sourced run a voice on its own issue. When a role raises `ROLE_NEEDS_INPUT` on a run
that came from `github:`, Dark Factory posts the question as a fresh comment on that issue,
records the comment's id on the `human_interactions` row in the same transaction that opens the
question, and still pauses at `WAITING_HUMAN` exactly as it does today.

Purpose: GIT-05. Until now a paused run was only answerable through `dark-factory resume --answer`
on the operator's own terminal — a human who never sees that terminal has no way to know the run
is waiting on them. This plan puts the question where the work was requested. It is also the
first half of the resume loop plan 10-04 closes: the `clarification_comment_id` written here is
the identifier the webhook handler compares against so Dark Factory never answers its own
question (10-RESEARCH.md Pitfall 2).

Output: the clarification-comment post wired into `_run_current_role`'s existing
`ROLE_NEEDS_INPUT` branch, guarded by D-05's "check the persisted identifier before acting" rule,
plus a unit suite over the body template and a db-tier proof against a real paused run.

Not in this plan: the inbound side — receiving a reply comment, resolving it to this interaction
and resuming the same `RoleExecution` — is plan 10-04 (GIT-06, D-01/D-02). The
`clarification_comment_id` and `github_comment_id` columns and the `HumanInteractionWrite` fields
that carry them already exist from plan 10-06.

**Two new module-level names in `orchestrator/runner.py`.**

`CLARIFICATION_COMMENT_PREFIX` is a module constant holding the fixed lead-in D-08 requires — a
short bold line naming Dark Factory as the asker, so a maintainer scrolling the issue can tell at
a glance that a machine asked. Keep it a constant, not an f-string built at the call site: a
constant is what makes "the prefix is fixed" checkable and what plan 10-04's self-comment filter
can reference if it ever needs to.

`build_clarification_comment(questions: Sequence[str]) -> str` is a pure function that returns the
prefix, a blank line, and `"\n".join(questions)` — the exact same text the `human_interactions`
row stores, so the comment and the persisted question can never disagree. It takes **only** the
question list. Do not give it a run id, a role name, an attempt number, a branch, a path or any
other parameter: a parameter it does not receive is a value it cannot leak, and that is the
cheapest possible enforcement of the no-internal-state prohibition. Its docstring states that
rule and why.
