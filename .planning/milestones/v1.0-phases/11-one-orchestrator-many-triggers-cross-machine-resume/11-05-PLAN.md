<objective>
Close the loop for a human. Plans 11-01 through 11-04 make the local→CI handoff work and prove it;
this plan makes it *usable* by somebody who did not write it — the workflow to add to their own
repository, the credential to provision and at what scope, the secrets that workflow needs, and
how to tell from the logs why a resume did not fire.

Purpose: D-04's `resume.yml` is the one artifact in this phase that Dark Factory does not ship and
cannot enforce — it lives in the deployer's repository, is written by the deployer, and is the
thing the whole dispatch path aims at. 11-PATTERNS.md found no analog for it anywhere in this
codebase, which is exactly why it needs writing down rather than inferring. And the credential it
needs is the one a deployer is most likely to over-grant: 11-RESEARCH.md Pitfall 4 establishes that
`actions: write` — the phrase in the decision record — is a *fine-grained* token permission name
with no equivalent checkbox on the classic-token screen, so a deployer following the decision
record literally either fails to find it or reaches for the much broader `repo` scope.

Second purpose: documentation that describes a YAML file rots silently. Task 2 makes the reference
workflow machine-checked — it must parse, declare the input the dispatcher sends, invoke the CLI
once, and carry no branch on run state. That last assertion is the documentation half of this
phase's first prohibition: the trigger must not become a second place where "what happens next" is
decided, and a reference workflow that grew a conditional would be exactly how that starts.

Output: one README section, bracketed by machine-readable sentinels, and one unit-tier guard.

Deliberately NOT in this plan: any production code (plans **11-01**, **11-02**); the proofs (plans
**11-02**, **11-03**); `.github/workflows/ci.yml` (plan **11-04**). And explicitly not in this
phase at all: a `dark-factory init` scaffold command that would generate `.dark-factory.yaml`,
starter role files and `resume.yml` for a new deployer — 11-CONTEXT.md records it under Deferred
Ideas as a genuine gap and a genuine new capability, not this phase's scope. The README section
should name that absence so a reader knows it is a decision, not an oversight.

The phase's single artifact index lives in `11-01-PLAN.md` under "Artifacts this phase produces".
</objective>

**New section, titled for what it does** (e.g. "## Finish a run in CI — the local → CI handoff"),
inserted after "### 5. When a process is killed while it owns a run" and before
"## Running the tests". Six parts, in this order:

1. **What this is.** One paragraph: a run that pauses for a human on your laptop does not have to
   be resumed on your laptop. When the human replies on the GitHub issue, the webhook receiver
   records the answer in Neon and then asks GitHub Actions to start a job that resumes the run —
   a genuinely different machine, with nothing carried over but the run id. State the invariant
   plainly: the trigger carries no lifecycle logic; every entry point reaches the same
   `advance(run_id)`.

2. **The deployment model**, from 11-CONTEXT.md's `<specifics>` block, as four numbered steps:
   install `dark-factory` as a dependency inside your own repository's toolchain; hand-author
   `.dark-factory.yaml` and `.dark-factory/roles/*.yaml` in your own repository, modelled on the
   ones this repository ships; add one small `resume.yml` workflow to your own repository; give
   your webhook receiver a `DISPATCH_GITHUB_TOKEN`. Say explicitly that a deployer does **not**
   clone or check out Dark Factory's own repository, because the pip-installable-package model is
   the thing that makes the rest of the section make sense. Close the part by naming the gap: there
   is no `dark-factory init` command to scaffold steps 2 and 3 yet — a deliberate deferral recorded
   in this phase's context, not an oversight.

3. **The full flow**, from 11-CONTEXT.md's five numbered steps, as a short numbered list: local
   `dark-factory run github:<owner>/<repo>#<n>` creates and drives the run and may pause
   `WAITING_HUMAN` with a clarifying comment on the issue; the human replies; GitHub delivers an
   `issue_comment` webhook, the receiver verifies its signature, resolves the pending interaction
   and records the answer; the receiver reads the run's own persisted `repository.github_owner` /
   `github_repo` and asks GitHub to dispatch `resume.yml` on that repository with the run id as
   input; a fresh Actions runner checks out the repository, installs `dark-factory` and runs
   `dark-factory resume <run_id>`, which re-materializes everything from Neon plus a fresh git
   worktree; the run reaches `COMPLETED` or pauses again and the loop repeats.

4. **The reference workflow.** Introduce it as content the deployer copies into their own
   repository at `.github/workflows/resume.yml`, and state plainly that Dark Factory neither ships
   nor validates this file — it is a reference, and the deployer owns it. Bracket the fenced YAML
   block with the two sentinel HTML comments `<!-- resume-workflow-reference: begin -->` and
   `<!-- resume-workflow-reference: end -->` on their own lines, immediately outside the fence;
   Task 2's guard locates the block by those sentinels, so their exact spelling is load-bearing and
   a one-line comment in the README should say so.

   The workflow itself: quote the trigger key (`"on":`) exactly as this repository's own `ci.yml`
   does, because YAML 1.1 parses a bare `on:` as the boolean `True`; declare
   `workflow_dispatch.inputs.run_id` as a required string with a description; declare
   `permissions: contents: read`; and give it one job with `runs-on: ubuntu-latest`, an explicit
   `timeout-minutes`, and three steps — `actions/checkout@v4`; an install step; and one step that
   runs `dark-factory resume "${{ inputs.run_id }}"` with `DATABASE_URL`, `DATABASE_URL_DIRECT`,
   `GITHUB_TOKEN` and whichever worker credential the deployer's roles use passed through `env:`
   from `${{ secrets.* }}`. No `if:` anywhere, no matrix, no second job, no conditional on run
   state — the workflow is a trigger, and a trigger that grows a branch on run state has started
   deciding what happens next, which is the one thing it must not do. Say that in a sentence under
   the block, not only in a comment inside it.

   Under the block, list the Actions secrets the deployer must set on their repository and what
   each is for, and state the exit-code contract the step inherits from the CLI: `0` for a run that
   reached a clean terminal state (including a fresh `WAITING_HUMAN` pause — the loop simply goes
   round again), `1` for a persisted `FAILED`, `2` for a bad invocation such as an unknown run id.
   A deployer needs this to read a red Actions run correctly.

5. **The dispatch credential.** Lead with the narrow shape and make the broad one visibly
   secondary: a **fine-grained** personal access token, scoped to the one target repository, with
   the `Actions: Read and write` permission — nothing else. Then the note that matters
   (11-RESEARCH.md Pitfall 4): the phrase `actions: write` is the fine-grained permission name and
   has no equivalent checkbox on the classic-token screen; a classic token needs the much broader
   `repo` scope instead, which works but grants far more than this call needs, and is therefore a
   documented fallback rather than an equal option. Name the variable `DISPATCH_GITHUB_TOKEN`,
   matching `.env.example` exactly, and say why it is a third token separate from `GITHUB_TOKEN`
   and `GITHUB_WEBHOOK_SECRET`: one field per credential purpose, so "did the infrastructure
   credential ever reach somewhere it should not" stays answerable from the field name alone.

6. **When the resume does not fire.** A four-row table of the receiver's dispatch outcomes and the

   durably recorded — a missing dispatch delays the resume, it never loses the answer — and that

Module docstring states why a documentation test exists here at all: `resume.yml` is the one
artifact of this phase that Dark Factory does not ship, cannot enforce and does not execute, so the
only thing standing between the reference and silent rot is a check that it still parses and still

lines, and returns the inner YAML string. Raise an `AssertionError` naming the count when the

block, looking it up under the string key `on` and then under the boolean key `True`. YAML 1.1

reference workflow does the same — but the guard must tolerate both, or it will fail for a reason
