Close the three test-infrastructure halves of G-11-3. Six of the gap's twelve CI failures, plus a
strictly worse latent sibling, come from test-layer frames that reach the process-global settings
accessor with no override: the shared real-sink log helper (5 failures), the clarification-comment
driver for `_run_current_role` (1 failure), and the live-runtime credential probe (0 current
failures, but a total collection abort the moment a worker CLI is on `PATH`).

consistently" — two settings-override idioms already exist at 14 unit-tier sites, and these files
adopted neither. Each fix below is applied at the *shared* layer rather than the call sites, so the
next test file inherits the property instead of rediscovering the requirement. The latent sibling is
fixed in the same plan because it is the identical class, strictly worse (zero tests run rather
than twelve failing), and already live: a sanitized full-tier run on this machine aborts at
collection today.

Output: a `real_log_sink` that is safe in a database-free process without weakening the redaction
suite that depends on it, a credential probe that degrades to a skip instead of an abort, and a
clarification-comment module that overrides settings for every branch of the function it drives.
</objective>

**The constraint that decides whether Task 1 is honest or destructive:**
`tests/unit/test_log_redaction.py` deliberately sets its own live-shaped database URL via

fake one, that value would no longer be a known secret, redaction would not fire on it, and those
assertions would fail — or, if the helper instead patched the accessor wholesale, they would pass
while proving nothing. The override must trigger **only on absence**. This is the single most
important implementation constraint in this plan.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process environment -> the settings choke point | Task 1 writes two credential-named variables into the running test process's own environment. Anything that reads settings inside that window sees them. |
| configured secret values -> the structlog sink | The redaction processor's known-secret map is derived from whatever settings object exists at log time. Task 1 changes which object that can be, so it changes what the redaction suite is actually proving. |
| worker credential presence -> live-suite skip decision | Task 3 changes how an unreadable credential is classified, which decides whether a live suite that would spend real money and touch a real repository runs or skips. |
