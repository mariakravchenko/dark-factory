<objective>
The tracer slice. One run stops mid-role to ask a human a question, releases its process cleanly, and is later resumed by a brand-new process that has nothing from the original but a run id and the database — wired end to end through every layer this phase touches, under a Postgres lease, with a runnable two-real-process proof.

**User story framing (MVP mode).** **As an** operator whose delivery run has hit a genuine ambiguity, **I want to** see the run stop with the question recorded, get my terminal back, and later type `dark-factory resume <run-id> --answer "..."` from anywhere, **so that** a multi-day human round trip costs me a database row rather than a process I have to babysit.

This is the plan after which a real user can do something they could not before: pause and resume a durable run. Everything before it added schema and vocabulary. It is production-quality, not a prototype — the lease, the fence and the heartbeat all ship complete here, and the expansion plans that follow (`02-04` the race and the reclaim, `02-05` the heartbeat and the no-transaction proof, `02-06` the generic mechanism and the redaction sweep) *prove* properties of this slice rather than adding missing layers to it.

Output: a working pause and a working `resume --answer`, both proven across a real process boundary.

  <action>
    Wire ONE path through every layer, end to end: a real `dark-factory run` process pauses on a scripted NEEDS_INPUT result and exits 0, and a second, brand-new `dark-factory resume --answer` process drives the same run to COMPLETED on the same attempt. One path only. Do not build the race proof, the expiry-reclaim proof, the slow-step proof, the no-transaction-across-the-worker proof or the redaction sweep — those are plans 02-04 through 02-06, and each proves a property of what you build here.

    **`src/dark_factory/orchestrator/lease.py` (new).** Ownership of a run, and nothing else. This module touches only `owner_token`, `lock_expires_at` and `updated_at`; it never writes a lifecycle column and never constructs an audit row, which is why it sits beside the one mutation path rather than inside it.

    Define `claim_lease(session, run_id, *, ttl_seconds) -> UUID | None`: generate a fresh `uuid4` token and execute exactly one statement — an update of `runs` setting the owner token, setting the lock expiry to the server clock function plus a `timedelta` of the TTL, and touching `updated_at`, guarded by `id` equal to the run, the status not in the terminal set, and the disjunction "owner token is null OR the lock expiry is earlier than the server clock", returning the run id. Return the token when a row came back and None when none did. One statement is the whole design: the update takes its own row lock for its duration, two concurrent claims serialise, and the loser re-evaluates its predicate against the now-committed row and matches nothing. Returning the id in the same statement is what removes the check-then-act window that a select-then-decide-then-update would open. Do not add a row-level select lock, an advisory lock or a skip-locked clause on top: a second coordination primitive for the same guarantee is the thing the project's constraints exist to prevent.

    Define `renew_lease(session, run_id, token, *, ttl_seconds) -> bool`: one update pushing the lock expiry to the server clock plus the TTL, guarded by `id` and by the owner token equalling this process's token, returning the run id; return whether a row came back. Define `release_lease(session, run_id, token) -> None`: one update setting both lease columns to null, guarded by `id` and the owner token, so a process can only ever release its own lease.

    Every expiry value in this module is a SQL expression combining the server clock function with a duration; every expiry comparison is a SQL predicate against that same clock function. Nothing in this module reads the process clock for a correctness decision — the one place `time` appears is the heartbeat's sleep between renewals, which is a delay and not a timestamp. This is the property that makes two machines in Phase 11 unable to disagree about whether an owner is alive.

    Define a frozen `LeaseHandle` carrying the `token` and a `threading.Event` named for lease loss. Define `LeaseNotAcquired(RuntimeError)` carrying the run id and the run's observed status, so a caller can report cleanly without re-reading the run.

    Define `run_lease(run_id, *, session_factory=new_session, ttl_seconds=None, heartbeat_seconds=None)` as a `contextlib.contextmanager` yielding a `LeaseHandle`. It resolves the TTL and interval from `Settings` when not supplied, claims through a short-lived session, and raises `LeaseNotAcquired` when the claim returns nothing — after logging, with the run id bound, that the run is owned by another process and this one is exiting without changes. On a successful claim it starts one daemon `threading.Thread` that loops on a stop `Event`'s timed wait so it wakes immediately on shutdown, and on each wake opens its **own** session — obtained by calling the session factory inside the thread, never by sharing the caller's — renews, and on a renewal that matches no row sets the lease-loss Event and returns.

    The `__exit__` path is the part that must be right on every exit, normal or exceptional: set the stop Event, join the thread with a short bounded timeout, then best-effort release the lease, swallowing and logging a release failure rather than masking the original exception. A heartbeat that keeps renewing after its owner has decided to stop holds the run hostage for the life of the process, and the run then looks merely slow rather than stuck — which is why the thread is never started outside this context manager and why `__exit__` has no early return.

    **`src/dark_factory/persistence/mutations.py`.** Extend the one mutation path; do not add a second writer.

    Add `LeaseLost(RuntimeError)` beside `ConcurrentTransition`, and export both. Add `HumanInteractionWrite`, a frozen `extra="forbid"` pydantic model mirroring `RoleExecutionWrite`, with `mode: Literal["ask", "answer"]`, an optional `role_execution_id`, an optional raw `question` and an optional raw `answer`. Like the other call-shape models it carries **raw** text: scrubbing is this module's job and never the caller's.

    Give `apply_transition` two new keyword parameters, both defaulting to None: `expected_owner_token: UUID | None` and `human_interaction: HumanInteractionWrite | None`. Inside the existing single transaction block, in this order: after the expected-status guard, when an expected owner token was supplied and the already-locked run row's owner token differs from it, raise `LeaseLost` naming both — the row is already locked for update, so this is a free, correct fence and no second select is needed. Then write the role execution as today. Then, when a human interaction was supplied, call a new `_write_human_interaction` helper. Then set the status, current role, current step and updated timestamp as today, and additionally, when the next status is in the stop set, set both lease columns to null. Then apply the counter increments and append the events as today.

    `_write_human_interaction(session, run_id, spec, known)` mirrors `_write_role_execution`. In `ask` mode it constructs the interaction row with status WAITING, the run id, the supplied role-execution id and the redacted question, applying `redact` at this call site exactly as the role-execution helper does for its result and error. In `answer` mode it selects, with a row-level update lock, the single interaction for this run whose status is WAITING, raises `LookupError` when there is none, and sets the redacted answer, the ANSWERED status and the answered timestamp from the server clock function. Locating the row inside the transaction rather than taking an id from the caller is deliberate: it keeps the find and the write in one atomic step, and the partial unique index guarantees there is at most one candidate.

    Update the module docstring: the write surface now also covers `human_interactions`, and the lease columns are cleared here whenever a transition reaches a stop status. Say why the *clear* lives here rather than in the lease module — the release must be atomic with the state change that made the run stop, so that a crash between the two is impossible.

    Note the invariant this preserves: the question text and the answer text pass through the same `redact` call site as every result, error and event payload. A new persisted text field that bypassed it would be an unrecoverable leak, because a secret is only redactable before it is written.

    **`src/dark_factory/persistence/repositories.py`.** Add `result: dict[str, Any] | None = None` to `LatestExecution` and populate it from the row. Add `pending_answer: str | None` to `RunState`, loaded by a third bound-parameterised select: the answer of the interaction for this run whose status is ANSWERED and whose role-execution id matches the latest role-execution row, or None. Add a small read helper `pending_question(session, run_id) -> str | None` returning the question of this run's WAITING interaction, or None, for `submit_answer`'s precondition check. Extend the module docstring's column-not-variable list with both new fields. `human_interactions` is a state table, not the audit log, so reading it here does not weaken the rule that control state never comes from folding events — say that explicitly, because the next reader will ask.

    **`src/dark_factory/orchestrator/lifecycle.py`.** Add one arm immediately after the failure arm: on the needs-input signal return the waiting status, the retained current role and the unchanged current step. Retaining the role is what lets a resume know where to go back to, exactly as the failure arm retains it. Update the module docstring's enumerated graph with the new edge. The function stays pure.

    **`src/dark_factory/orchestrator/runner.py`.** Four changes.

    Refactor the per-step body into a private function that takes the run id and the held owner token and assumes the lease is already held. `advance` becomes: open the lease context, then call that private function; `drive` becomes: open the lease context once and loop the private function until the status is in the stop set, so the lease is claimed once per drive rather than once per step and a re-claim can never race the process's own token. Keep the existing generous iteration bound and its loud exhaustion error, keep the structlog context binding, and keep both `_maybe_crash_after` call sites exactly where they are.

    Extend the early-return guard so a run whose status is in the stop set — not merely the terminal set — returns immediately without writing. Without this, a run sitting in WAITING_HUMAN falls through and the worker is called again with no answer, which is the single most likely way this feature silently misbehaves. Only `submit_answer` moves a run out of the waiting status.

    In the per-step function, make the execute-versus-resume choice from the persisted latest role-execution status: when it is the resuming marker, validate the persisted result back into a `WorkerResult` and call the worker's resume method with the context, that previous result and the state's pending answer; otherwise call execute. Read the decision from the column, never from anything held in memory — that is what makes a crash between storing the answer and dispatching the role recoverable by the next process. Extend `_build_context` with the pending answer under an `answer` key. Add module constants for the two new role-execution marker strings rather than inlining the literals, beside the existing running, completed and failed markers.

    Add a needs-input branch to the signal dispatch, mirroring the failure branch's shape: the role-execution status becomes the waiting marker, the result field carries the serialised needs-input outcome (it is what a resume validates back into `previous`, so it must be stored, not discarded), the worker session id is carried through, the events are QUESTION_CREATED with the role and the questions and then RUN_PAUSED with the role, and a `HumanInteractionWrite` in `ask` mode carries the newline-join of the result's questions and the latest role-execution's id. Pass the held owner token as the expected owner token on this and on every other `apply_transition` call the step makes. Then check the lease-loss Event immediately after the worker call returns and before building any write: when it is set, log, discard the worker result, write nothing at all and re-raise as a lease loss. The Event is only a fast abort; the commit itself is fenced by the token, because the Event races with the worker call returning.

    Because the branch keys off the signal and not the role name, every present and future pipeline node gets the ask-a-human mechanism with no per-role code. That is the whole of HITL-01 and it is worth a comment.

    **`src/dark_factory/orchestrator/answers.py` (new).** `submit_answer(run_id, answer, *, session_factory=new_session, pipeline=DEFAULT_PIPELINE) -> RunStatus`. Define `NotWaitingForHuman(RuntimeError)` and `NoPendingInteraction(RuntimeError)`.
