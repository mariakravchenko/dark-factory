<objective>
Close the loop: make the Developer's bounced attempt actually *receive* the feedback that
caused the bounce. QA's structured issues and the quality gate's real command output reach the
next `RoleContext` as durable artifact content resolved by `ContextBuilder` from declarations
in `DEVELOPMENT.yaml` — not as an in-memory value and not as a Python special case.

Purpose: LOOP-01 and LOOP-02's payload half. Plan 09-02 made the run loop; without this plan
the Developer re-runs with exactly the context it had the first time and the loop is
information-free.

Output: an `optional_inputs` role-config key and its lenient two-strategy resolution in
`ContextBuilder`, the two declarations on `DEVELOPMENT.yaml`, and a db-tier proof that a
bounced Developer attempt sees both payloads.

**Resolved design question.** 09-RESEARCH.md Open Question 1 asked how
`verification/quality_gate.json` reaches `ContextBuilder`, since it is no role's declared
output and the gate has no `role_executions` row to hang an `ArtifactReference` on. This plan
takes **direction (a)**: a lenient optional-input path plus a second, distinct resolution
strategy that reads the `verification/` tree directly. Direction (b) — minting a synthetic
`ArtifactReference` against QA's own row and declaring `quality_gate.json` among QA's
`outputs` — was rejected: `collect_role_artifacts` validates a role's declared outputs against
what its *worker* reported, and it runs *before* the gate does, so QA's attempt would fail its
own artifact contract on a file the orchestrator has not written yet. It would also record an
`artifacts` row for orchestrator-generated content, blurring the ART-01/ART-03 line between
what a worker produced and what Dark Factory produced.

**Sequencing is load-bearing (09-RESEARCH.md Pitfall 2).** The `ContextBuilder` change and the
`DEVELOPMENT.yaml` change land in the *same* task. Landing the config change alone — or adding
these filenames to the existing mandatory `inputs:` list — makes `_resolve_input` raise
`MissingArtifactContentError` on the Developer's first attempt of *every* run, not just a
bounce, because DEVELOPMENT is upstream of QA and QA has no `COMPLETED` row yet.
</objective>

**`src/dark_factory/context/builder.py`**: add one new private resolver and one new
declaration-order-preserving extension to `build_role_context`.

The new `_resolve_optional_input(session, repo_root, run_id, state, filename) ->
ArtifactInput | None` tries two strategies in a fixed order and returns `None` when neither
yields content:

Strategy one is the existing declared-output path: call `_producing_role(state, filename)`.
When it resolves, continue exactly as `_resolve_input` does — `_latest_completed_execution`,
then the `ArtifactReference` lookup keyed on `role_execution_id` and `type`, then
`read_artifact_text` — but catch `MissingArtifactContentError` and return `None` instead of
letting it propagate. This is the `verdict.json` case: QA declares it as an output, so the
lookup is the ordinary one; it is only *absent* on the Developer's first attempt, before QA has
ever completed. Note that `_latest_completed_execution` filters on `RoleExecution.status ==
"COMPLETED"`, which is exactly why plan 09-02 kept a bounced attempt at `"COMPLETED"` — a
bounced QA attempt must remain visible here.

Strategy two runs only when `_producing_role` raises `ArtifactContractError`, meaning no role
in the snapshot declares this filename as an output. Read the relative path
`verification/<filename>` under `run_root(repo_root, run_id)` with `read_artifact_text`,
catching `MissingArtifactContentError` and returning `None`. On success return an
`ArtifactInput` with `filename` set to the bare filename, `path` set to the relative
`verification/<filename>`, `produced_by` set to the string `"quality_gate"`, and the file's
content. This is the `quality_gate.json` case and it deliberately touches neither
`_producing_role` nor the `artifacts` table: per D-01 the gate has no `role_executions` row, and
`ArtifactReference.role_execution_id` is a required non-nullable column with nothing to point
at. `"quality_gate"` is not one of the six `RunStatus` role values, so it names the producer
honestly without implying a pipeline role.

Do **not** catch `ArtifactTooLargeError` in either strategy. An oversized feedback artifact is a
real problem that must surface, matching the "never silently truncate" rule the rest of this
package already follows; swallowing it would hand the Developer a silently missing failure
report.

Use no directory listing, glob or tree walk anywhere in this resolver — the path is constructed
from the declared filename and resolved through `resolve_under_run_root` inside
`read_artifact_text`. `tests/unit/test_no_tree_walk.py` AST-scans this package for exactly that.

In `build_role_context`, after the existing mandatory `inputs` comprehension, append the
resolved optional inputs in declaration order, skipping every `None`, reading the declaration
list with the same defensive idiom the rest of the function uses so a legacy bare-string
snapshot entry with no such key yields an empty list. `RoleContext` itself gains no new field —
resolved optional inputs are ordinary `ArtifactInput` entries in the existing `inputs` list, so
no worker adapter needs a change.

Extend the module docstring's CTX-02 paragraph to record the second named-path family: a
role's declared `optional_inputs` resolve either through the same `outputs` declaration path as
`inputs` or, for an orchestrator-written `verification/` file that no role declares, through a
direct read of that one named path — still a fixed, small set of named paths, still never a
directory read.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
