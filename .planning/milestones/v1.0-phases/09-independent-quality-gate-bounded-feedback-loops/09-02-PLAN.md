<objective>
Turn the two terminal rejections plan 09-01 established into bounded feedback loops: a QA
verdict FAIL and a quality-gate FAIL each send the run back to the role immediately before the
pipeline's terminal role, under its own configured iteration cap, and exhausting either cap
ends the run in `FAILED` with the reason and every attempt persisted.

Purpose: LOOP-02, LOOP-03 and LOOP-04. This is the phase's headline control-flow change — it
makes `lifecycle.transition()` able to move a run *backwards* through the pipeline for the
first time, while keeping it the single place a next position is computed.

Output: `Signal.ROLE_BOUNCED`, `previous_node`, the new `transition()` arm, the
`EventType.ROLE_BOUNCED` audit tie, the cap-check-then-choose-signal logic in
`_run_current_role`, and db-tier proofs of the bounce and of both exhaustion paths.

**On D-04's one-way rating:** 09-CONTEXT.md D-04 is a locked decision the developer already
made, so the `checkpoint:decision` at the top of this plan does not re-ask whether to add
`Signal.ROLE_BOUNCED` (re-gating a settled choice is checkpoint fatigue). It settles only the
part D-04 left open and that 09-RESEARCH.md flags as *inferred* rather than decided —
Assumption A3 and Open Question 2, the `role_executions.status` a bounced attempt carries and
whether the bounce earns its own `EventType` member. Both are persisted contracts, so the
confirmation happens before the implementing task rather than after.

**Not in scope here:** actually *delivering* the QA issues and the gate output to the
Developer's next prompt. The bounce lands the run back on the Developer with a fresh attempt
row; plan 09-03 makes `ContextBuilder` resolve `verdict.json` and `quality_gate.json` into
that attempt's `RoleContext`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo config → orchestrator control flow | `retry.*_max_iterations` from `.dark-factory.yaml` bounds how many times the orchestrator will re-dispatch a worker |
| concurrent processes → `runs` counter columns | two processes may attempt the same run's step; the counters are mutable shared state |
| worker outcome → run direction | a worker's own result now indirectly influences whether the run moves backwards |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-07 | Denial of Service | the feedback loop re-dispatching a worker forever | high | mitigate | The cap is read from the persisted snapshot and compared **before** the signal is chosen; a counter at or over its cap yields `ROLE_FAILED`, never `ROLE_BOUNCED`. A cap of 0 makes the first rejection terminal with no special case. `_MAX_DRIVE_ITERATIONS` remains as the outer loud-failure backstop. Proved by `tests/db/test_iteration_cap_exhaustion.py`. |
| T-09-08 | Tampering | a lost or racing process double-incrementing an iteration counter, silently widening the cap | high | mitigate | The increment rides `apply_transition`'s existing `counter_increments` parameter inside the same transaction, under the same `with_for_update` row lock, behind the same `expected_status` and `expected_owner_token` fences as every other field in that call. No second write site for these two columns is introduced — asserted by a grep for lock calls outside `persistence/mutations.py`. |
| T-09-09 | Repudiation | a bounce that is indistinguishable in the audit trail from a normal completion, or that falsely reads as a dead run | medium | mitigate | A purpose-built `ROLE_BOUNCED` event carrying the reason, the counter name, its pre-increment value and its cap — emitted in addition to the attempt's `ROLE_COMPLETED`, and explicitly never in place of, nor alongside, `ROLE_FAILED` / `RUN_FAILED`. |
| T-09-10 | Information Disclosure | the `ROLE_BOUNCED` and extended `RUN_FAILED` payloads carrying run detail into `run_events` | low | mitigate | Both payloads carry only a role name, a fixed reason token, a counter name and two integers — no captured output and no free text. They are written through `apply_transition`, which applies `redact()` to every payload it writes, so the control is defence in depth rather than the only line. |

No upper bound is added — the operator who owns the repo owns the cost. |
