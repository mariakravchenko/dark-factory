<objective>
**As a** Dark Factory operator, **I want to** know that a worker subprocess receives only the minimum environment its role needs and never sees an infrastructure credential, **so that** handing an autonomous agent a shell inside my repository cannot hand it my database URL or my GitHub token.

This plan expands the proven `ToolRegistry` slice outward along the credential axis. Task 1 builds `build_worker_env()` and proves ROADMAP SC2 the only way it can honestly be proven — by spawning a real operating-system process and asking it what environment it actually got. Task 2 gives that builder a genuine production caller: `shell.execute`'s real implementation, which is the capability a Developer or QA role uses to run a command, and which therefore is the first place a worker-adjacent process is ever spawned by capability-gated code.

Purpose: SEC-03 and TOOL-04 are spec-level constraints of this project, and Phase 7 will wire a real `claude` subprocess to this exact function — proving it standalone now means Phase 7 inherits a boundary that is already tested rather than one it has to invent under deadline.
Output: `src/dark_factory/tools/env.py` (`build_worker_env`, `WORKER_ENV_ALLOWLIST`, the `shell.execute` implementation), the cross-process env-dump harness, and the three proof modules.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dark Factory process → worker subprocess | The process holding `DATABASE_URL` / `GITHUB_TOKEN` spawns a process that must never see them; the environment mapping is the crossing point |
| capability caller → spawned command | The command and its arguments originate outside this function; they must never be able to select the executable or inject a second command |
| spawned process → captured output | The child's stdout/stderr are captured and may be persisted or logged, so they are an egress path for anything the child echoes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Information Disclosure | `build_worker_env` (`tools/env.py`) | critical | mitigate | The mapping is built by comprehension over `WORKER_ENV_ALLOWLIST` starting from an empty dict; no parent-wide copy, spread, or exclusion-filter form is used. Structurally guarded by `tests/unit/test_no_environ_copy.py`, which rglobs `src/dark_factory/`, and behaviourally by the cross-process dump in `tests/integration/test_worker_env_boundary.py` |
| T-06-02 | Tampering | `shell_execute` (`tools/env.py`) | high | mitigate | The command crosses as an explicit argument sequence passed straight to `subprocess.Popen`; the implementation never joins it into a string, never enables shell interpretation, and rejects a bare string argument with a typed error rather than silently splitting it |
| T-06-12 | Denial of Service | `shell_execute` (`tools/env.py`) | medium | mitigate | Every spawn carries an explicit `timeout`; on expiry the whole process group is terminated (`start_new_session=True` at spawn so the group id is the child's own), and the result is returned with `timed_out=True` and whatever partial output was captured — never an unbounded wait |
| T-06-13 | Information Disclosure | captured `shell.execute` stdout/stderr | medium | mitigate | The captured streams are returned to the caller and are not logged or persisted by this module; any caller that persists them crosses the single `redact()` pass in `persistence/mutations.py` (SEC-02), which substitutes every value `Settings.known_secret_values()` reports |
| T-06-14 | Elevation of Privilege | `shell.execute` invoked by a role without the grant | high | mitigate | The grant check is `ToolRegistry.invoke()`'s, unchanged from plan 06-01 — `shell_execute` performs no permission logic of its own and must not, so there is exactly one place the decision is made. Proven by the ungranted-role arm of `tests/unit/test_shell_execute.py` |
| T-06-15 | Information Disclosure | credential passed via argv rather than env | high | mitigate | `build_worker_env` is the only channel for the credential; `shell_execute` never accepts a credential parameter and never appends one to the argument sequence, so the value cannot reach a process listing |
