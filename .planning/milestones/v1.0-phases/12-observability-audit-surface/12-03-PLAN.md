<objective>
Close the one live credential-disclosure gap 12-RESEARCH.md found by reading the
current source: the GitHub clarification-comment body is built straight from the
raw `WorkerResult.questions` and handed to `create_comment` with no `redact()`
call anywhere on that value.

Purpose: a GitHub issue comment is an external, permanent, non-revocable sink. The
sibling write — `human_interactions.question` — *is* correctly redacted inside
`apply_transition`, which is exactly what makes this gap easy to miss and
expensive when it fires: the database looks clean while the public issue carries
the credential forever. This is the phase's one `high`-severity threat under the
configured ASVS Level 1 / block-on-`high` policy, so it is remediated by a task,
not noted.

Output: the redacted body on the `ROLE_NEEDS_INPUT` path, a widened-with-intent
redact-argument allowlist, and a db-tier proof.

  <action>
In `runner.py`'s `Signal.ROLE_NEEDS_INPUT` branch, replace the single `comment_body = build_clarification_comment(result.questions)` statement with two statements:

1. bind the unscrubbed text to a local named exactly `clarification_body`, built by the existing `build_clarification_comment(result.questions)` call;
2. bind `comment_body` to `redact(clarification_body, known_secrets=get_settings().known_secret_values())`.

Then leave the rest of the branch structurally unchanged, so both `_find_own_clarification_comment(client, owner, repo, issue_number, body=comment_body)` and `client.create_comment(..., body=comment_body)` consume the scrubbed value. Redacting once, before the lookup, is what keeps D-05's idempotency intact: the existence check compares the body text against Dark Factory's own already-posted comments, so if the lookup compared raw text while the create posted scrubbed text, every resumed attempt would fail to recognise its own comment and post a duplicate.

Scrub the joined body rather than each question individually. `redact` is a `str`-in / `str`-out call on a string, and scrubbing the assembled text covers both the question content and the `CLARIFICATION_COMMENT_PREFIX` header in one pass, with no list comprehension for a reader to mis-read as a per-element transform.

**The local's name is load-bearing and is not a style choice.** `tests/integration/test_redaction_interactions.py::test_the_interaction_writer_scrubs_at_the_one_mutation_path_call_site` runs two independent assertions over the `ast.unparse`d text of every `redact(` first positional argument in `runner.py`: it must appear in `_RUNNER_PERMITTED_REDACT_ARGUMENTS`, and it must NOT contain the lowercased substring `question` or `answer`. A name carrying either of those tokens, or an inline expression that passes `build_clarification_comment(result.questions)` directly into `redact`, trips the second assertion and cannot be allowlisted around — that assertion exists to guarantee the human-interaction question and answer are scrubbed exclusively inside `_write_human_interaction`, and it must keep holding. `clarification_body` satisfies both checks.

Widen `_RUNNER_PERMITTED_REDACT_ARGUMENTS` from its current one-entry frozenset to a two-entry frozenset, adding the new local's name, and extend the comment block immediately above it with a third bullet in the existing style: name this plan, name the requirement it serves, and state what the expression is (the assembled clarification-comment text, scrubbed before both the GitHub existence check and the `create_comment` call). The allowlist is designed to be widened deliberately and never silently; this is the deliberate widening, recorded in the place a future reader will look.

Make no change to `build_clarification_comment` itself. Its own docstring makes a narrower promise — it receives only the question list, so a parameter it does not take is a value it cannot leak (T-10-12) — and moving redaction inside it would make that function's single responsibility two.

Add no second `get_settings()` read if one is already live in the surrounding scope; if the branch has no settings object in hand, call `get_settings().known_secret_values()` inline exactly as the sibling `except GitHubError` arm in the same branch already does. Note that plan 11-08 installed a declared-inventory AST guard keyed on `(relative path, enclosing-function qualname, per-scope occurrence counter)` over every `get_settings()` call site; adding a call inside `_run_current_role` changes that function's per-scope occurrence count, so the guard's declared inventory must be updated in the same commit if the executor's run surfaces it.
